# PART ONE: INTRODUCTION TO CLOUD & DISTRIBUTED SYSTEMS

## Chapter 1: What Are Cloud & Distributed System Patterns?

**Understanding the Basic Concept**

A distributed system is a collection of independent computers that appear to users as a single coherent system. Cloud systems take this concept further, adding elasticity, on-demand resources, and global scale.

**Why Distributed Systems Are Different**

Building distributed systems is fundamentally harder than building single-node systems because:

1. **Partial Failures:** In a single system, something either works or fails entirely. In distributed systems, parts can fail while others continue.

2. **Network Unreliability:** The network can drop, delay, or reorder messages. You cannot trust the network.

3. **No Shared Memory:** Processes don't share memory, so coordination requires explicit communication.

4. **Clock Skew:** Different machines have different times. You cannot rely on timestamps for ordering.

5. **Consistency Trade-offs:** You cannot have strong consistency, high availability, and partition tolerance simultaneously (CAP Theorem).

**What Are Cloud & Distributed System Patterns?**

Cloud and distributed system patterns are proven solutions to recurring problems in building large-scale, distributed applications. They address challenges like:

- **Resilience:** How to handle failures gracefully
- **Scalability:** How to grow from one user to billions
- **Deployment:** How to release new versions without downtime
- **Communication:** How services find and talk to each other
- **Data Management:** How to store and retrieve data at scale
- **Observability:** How to understand what's happening in complex systems

**Think of it this way.** Building a distributed system is like running a global logistics company. You have warehouses (servers) across the world, trucks (network calls) that can get delayed, packages (data) that can get lost, and customers (users) who expect reliable service. You need patterns for:

- **Redundancy:** Having backup warehouses if one burns down
- **Retries:** Sending a package again if it gets lost
- **Load Balancing:** Distributing packages across warehouses
- **Circuit Breaking:** Stopping shipments to a warehouse that's backed up
- **Canary Deployments:** Testing new processes with one truck before scaling

**The Patterns in This Book**

This book covers 15 essential patterns organized into categories:

1. **Resilience Patterns:** Circuit Breaker, Retry, Bulkhead, Health Check
2. **Deployment Patterns:** Blue-Green, Canary
3. **Network Patterns:** Sidecar, Service Mesh, Gateway Routing, API Composition, Load Balancing, Leader Election
4. **Data Patterns:** Distributed Cache, Sharding
5. **Control Patterns:** Rate Limiting

## Chapter 3: The CAP Theorem and Its Implications

**What is the CAP Theorem?**

The CAP Theorem, formulated by Eric Brewer in 2000, states that a distributed system can only provide two of three guarantees simultaneously:

- **Consistency (C):** All nodes see the same data at the same time
- **Availability (A):** Every request receives a response (not an error)
- **Partition Tolerance (P):** The system continues to operate despite network partitions

**The Reality of Distributed Systems**

In practice, network partitions are inevitable in distributed systems. Therefore, you must choose between Consistency and Availability when a partition occurs.

**The Three Choices**

| Choice | What You Get | What You Lose | Example Systems |
|--------|--------------|---------------|-----------------|
| **CP** (Consistency + Partition Tolerance) | Strong consistency, data never inconsistent | Availability during partition | ZooKeeper, etcd, HBase |
| **AP** (Availability + Partition Tolerance) | Always available, system stays up | Data may be temporarily inconsistent | Cassandra, CouchDB, DynamoDB |
| **CA** (Consistency + Availability) | Strong consistency and availability | Fails during network partitions | Traditional relational databases (single-node) |

**Practical Implications**

**Choosing CP (Consistency + Partition Tolerance)**

Choose CP when:
- Data correctness is critical (banking, inventory)
- Temporary unavailability is acceptable
- You can retry operations later

**Choosing AP (Availability + Partition Tolerance)**

Choose AP when:
- System must always be available (social media, e-commerce)
- Some inconsistency is tolerable
- You can reconcile data later (eventual consistency)

**ACID vs BASE**

| Aspect | ACID | BASE |
|--------|------|------|
| Philosophy | Strong consistency | Eventual consistency |
| Availability | Lower | Higher |
| Performance | Lower | Higher |
| Use Case | Banking, finance | Social media, IoT |
| Examples | SQL Databases | NoSQL Databases |

**How Patterns Relate to CAP**

The patterns in this book help you navigate these trade-offs:

- **Circuit Breaker:** Helps maintain availability during failures (AP-oriented)
- **CQRS/Sharding:** Enable scaling while managing consistency
- **Distributed Cache:** Improves availability but may have stale data
- **Leader Election:** Provides consistency for coordination tasks

## Chapter 4: Core Concepts in Distributed Systems

**Essential Concepts You Must Understand**

**1. Latency vs Throughput**

- **Latency:** Time to complete a single operation (milliseconds)
- **Throughput:** Number of operations completed per second

**Trade-off:** Higher throughput often means higher latency (queuing)

**2. Consistency Models**

| Model | Description | Example |
|-------|-------------|---------|
| Strong Consistency | All reads see latest write | Relational DB (ACID) |
| Eventual Consistency | Reads may see stale data | DNS, Cassandra |
| Causal Consistency | Related operations ordered | Some NoSQL systems |
| Read Your Writes | User sees their own writes | Session consistency |

**3. Quorum**

A quorum is the minimum number of nodes that must agree to perform an operation.

- **Read Quorum:** Number of nodes that must respond to a read
- **Write Quorum:** Number of nodes that must acknowledge a write

**Formula:** To maintain consistency, read quorum + write quorum > total nodes

**4. Leader Election**

In a cluster, one node is elected as leader to coordinate operations. Other nodes are followers. If leader fails, a new leader is elected.

**5. Replication**

Copying data to multiple nodes for:
- **Availability:** If one node fails, others serve requests
- **Durability:** Data survives node failures
- **Read Scalability:** Multiple nodes handle read traffic

**Types:**
- **Synchronous:** Wait for all replicas (strong consistency, higher latency)
- **Asynchronous:** Write immediately, replicate later (eventual consistency, lower latency)

**6. Partitioning (Sharding)**

Splitting data across multiple nodes so each node handles a subset of the data. Allows horizontal scaling.

**7. Idempotency**

An operation is idempotent if performing it multiple times has the same effect as performing it once. Essential for retries.

**Example:** DELETE is idempotent; increment is not.

**8. Backpressure**

When a system is overloaded, it signals upstream to slow down. Prevents cascading failures.

**9. Thundering Herd**

When many clients simultaneously request the same resource (e.g., after a cache expiration). Patterns like singleflight prevent this.

**10. Tail Latency**

Long-tail latencies (99th percentile) matter more than average. In distributed systems, the slowest component determines overall latency.

**11. Byzantine Faults**

Failures where nodes behave arbitrarily (malicious, corrupted). Byzantine Fault Tolerance (BFT) is complex and expensive.

**12. Exponential Backoff**

Retry strategy where wait time increases exponentially. Prevents overload during recovery.

**13. Jitter**

Random variation added to retry timers to prevent synchronized retries (thundering herd).

**14. Fallback**

Alternative behavior when a request fails (cached data, default values).

**15. Rate Limiting**

Controlling the rate of requests to prevent overload. Algorithms: token bucket, leaky bucket, sliding window.

# PART TWO: RESILIENCE PATTERNS

## Chapter 5: Circuit Breaker Pattern

**Detailed Explanation**

The Circuit Breaker pattern prevents a service from repeatedly attempting to execute an operation that's likely to fail. It monitors failures and "trips" when failures exceed a threshold, allowing the failing service time to recover.

**Understanding the Problem**

In distributed systems, services depend on other services. When a downstream service fails or becomes slow:

1. **Threads Block:** Waiting for responses that never come
2. **Resource Exhaustion:** Thread pool fills up, new requests wait
3. **Cascading Failure:** Failure spreads to upstream services
4. **No Recovery:** The failing service gets hammered with requests, never recovers

**The Solution**

The Circuit Breaker pattern monitors failures. When failures reach a threshold, the circuit "trips" to OPEN. All subsequent calls fail immediately without attempting the operation. After a timeout, the circuit goes to HALF-OPEN to test recovery. If test calls succeed, the circuit closes. If they fail, it opens again.

**Three States**

1. **CLOSED:** Normal operation. Calls go through. Failures are counted.
2. **OPEN:** Circuit is tripped. Calls fail immediately without attempting.
3. **HALF-OPEN:** Limited test calls allowed. If successful, circuit closes. If any fail, circuit reopens.

**Implementation Example**

```java
public class CircuitBreaker {
    private enum State { CLOSED, OPEN, HALF_OPEN }
    
    private State state = State.CLOSED;
    private int failureCount = 0;
    private long openStartTime = 0;
    private int halfOpenSuccessCount = 0;
    
    private final int failureThreshold;
    private final long timeoutMs;
    private final int halfOpenMaxCalls;
    private final int successThreshold;
    
    public CircuitBreaker(int failureThreshold, long timeoutMs, 
                          int halfOpenMaxCalls, int successThreshold) {
        this.failureThreshold = failureThreshold;
        this.timeoutMs = timeoutMs;
        this.halfOpenMaxCalls = halfOpenMaxCalls;
        this.successThreshold = successThreshold;
    }
    
    public synchronized <T> T execute(Supplier<T> operation) 
            throws Exception {
        // Check current state
        if (state == State.OPEN) {
            if (System.currentTimeMillis() - openStartTime > timeoutMs) {
                state = State.HALF_OPEN;
                halfOpenSuccessCount = 0;
            } else {
                throw new CircuitOpenException("Circuit is open");
            }
        }
        
        // Try the operation
        try {
            T result = operation.get();
            // Success handling
            handleSuccess();
            return result;
        } catch (Exception e) {
            handleFailure(e);
            throw e;
        }
    }
    
    private void handleSuccess() {
        if (state == State.HALF_OPEN) {
            halfOpenSuccessCount++;
            if (halfOpenSuccessCount >= successThreshold) {
                state = State.CLOSED;
                failureCount = 0;
                System.out.println("Circuit closed after recovery");
            }
        } else {
            // Reset failure count on success in CLOSED state
            failureCount = 0;
        }
    }
    
    private void handleFailure(Exception e) {
        if (state == State.HALF_OPEN) {
            // Failure in half-open state immediately opens circuit
            state = State.OPEN;
            openStartTime = System.currentTimeMillis();
            halfOpenSuccessCount = 0;
            System.out.println("Circuit opened after half-open failure");
        } else if (state == State.CLOSED) {
            failureCount++;
            if (failureCount >= failureThreshold) {
                state = State.OPEN;
                openStartTime = System.currentTimeMillis();
                System.out.println("Circuit opened after " + 
                    failureCount + " failures");
            }
        }
    }
}
```

**When to Use Circuit Breaker**

**Suitable Situations:**

1. When calling remote services (microservices, external APIs)
2. When making database calls
3. When failures are likely and costly
4. When you want to give failing services time to recover
5. To prevent cascading failures

**Real-World Use Cases:**

- **Microservices:** Protecting service-to-service calls
- **API Gateway:** Protecting upstream services
- **Database Access:** Handling database connection failures
- **Third-Party APIs:** Graceful handling of external outages
- **Message Queues:** Preventing consumer overload

**Advantages**

1. **Fail Fast:** No waiting for timeouts
2. **Prevents Cascading Failures:** Stops failure propagation
3. **Automatic Recovery:** Tests for recovery automatically
4. **Resource Protection:** Saves threads and connections
5. **Self-Healing:** System recovers without manual intervention

**Disadvantages**

1. **Added Complexity:** Another component to configure
2. **Tuning Required:** Thresholds need per-service tuning
3. **State Management:** Need to share state across instances
4. **False Positives:** Can trip due to transient issues
5. **Not Suitable for All Failures:** Some failures need immediate retry

**Comparison with Other Patterns**

| Pattern | Purpose | Difference |
|---------|---------|------------|
| Circuit Breaker | Stop calling failing services | Trips on failures |
| Retry | Retry transient failures | Attempts again |
| Timeout | Bound wait time | Works together |
| Bulkhead | Isolate resources | Different mechanism |

**Best Practices**

1. **Configure Appropriately:** Different thresholds for different services
2. **Use Half-Open Testing:** Verify recovery before closing
3. **Monitor Circuit State:** Track trips, recovery times
4. **Share State Across Instances:** Use distributed cache for cluster-wide state
5. **Combine with Timeout:** Always set timeouts on calls

## Chapter 6: Retry Pattern

**Detailed Explanation**

The Retry pattern automatically retries failed operations when failures are transient (network issues, temporary service unavailability, resource contention).

**Understanding the Problem**

In distributed systems, many failures are transient:
- Network packet loss
- Service restarting
- Database connection pool full
- Load balancer rebalancing
- Temporary resource exhaustion

These failures often resolve themselves if you wait and try again. Without retries, transient failures become user-visible errors.

**The Solution**

The Retry pattern automatically retries failed operations with:
- **Limited Retries:** Stop after max attempts
- **Backoff Strategy:** Wait between retries
- **Jitter:** Add randomness to prevent thundering herd
- **Idempotency:** Ensure retries don't cause duplicates

**Retry Strategies**

| Strategy | Description | Example |
|----------|-------------|---------|
| Fixed Delay | Same wait between retries | 1s, 1s, 1s |
| Linear Backoff | Increase by fixed amount | 1s, 2s, 3s |
| Exponential Backoff | Double each time | 1s, 2s, 4s, 8s |
| Exponential + Jitter | Add randomness | 1s, 2.3s, 4.7s, 9.1s |

```java
public class RetryHandler {
    private final int maxRetries;
    private final long initialDelayMs;
    private final long maxDelayMs;
    private final double backoffMultiplier;
    private final List<Class<? extends Exception>> retryableExceptions;
    private final Random random = new Random();
    
    public RetryHandler(int maxRetries, long initialDelayMs, 
                        long maxDelayMs, double backoffMultiplier,
                        List<Class<? extends Exception>> retryableExceptions) {
        this.maxRetries = maxRetries;
        this.initialDelayMs = initialDelayMs;
        this.maxDelayMs = maxDelayMs;
        this.backoffMultiplier = backoffMultiplier;
        this.retryableExceptions = retryableExceptions;
    }
    
    public <T> T execute(Supplier<T> operation) throws Exception {
        Exception lastException = null;
        
        for (int attempt = 0; attempt <= maxRetries; attempt++) {
            try {
                return operation.get();
            } catch (Exception e) {
                lastException = e;
                
                // Check if we should retry
                if (!shouldRetry(e, attempt)) {
                    throw e;
                }
                
                // Calculate wait time
                long waitTime = calculateWaitTime(attempt);
                System.out.println("Retry attempt " + (attempt + 1) + 
                    " after " + waitTime + "ms");
                
                try {
                    Thread.sleep(waitTime);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw e;
                }
            }
        }
        
        throw lastException;
    }
    
    private boolean shouldRetry(Exception e, int attempt) {
        // Don't retry if max attempts reached
        if (attempt >= maxRetries) {
            return false;
        }
        
        // Check if exception is retryable
        for (Class<? extends Exception> retryable : retryableExceptions) {
            if (retryable.isInstance(e)) {
                return true;
            }
        }
        
        return false;
    }
    
    private long calculateWaitTime(int attempt) {
        // Exponential backoff
        double exponential = Math.pow(backoffMultiplier, attempt);
        long waitTime = (long) (initialDelayMs * exponential);
        
        // Add jitter (up to 30% of wait time)
        long jitter = (long) (waitTime * random.nextDouble() * 0.3);
        waitTime += jitter;
        
        // Cap at max delay
        return Math.min(waitTime, maxDelayMs);
    }
}

// Usage
RetryHandler retry = new RetryHandler(
    3,                // max 3 retries
    100,              // initial delay 100ms
    5000,             // max delay 5s
    2.0,              // double each time
    Arrays.asList(TimeoutException.class, IOException.class)
);

// Use with service call
retry.execute(() -> {
    return externalService.call();
});
```

**When to Use Retry Pattern**

**Suitable Situations:**

1. When failures are known to be transient
2. When operations are idempotent (safe to retry)
3. When you have backoff strategies to avoid overwhelming services
4. When you have timeouts to bound total wait time
5. When calling external services with transient issues

**Situations to Avoid:**

1. When failures indicate permanent errors (4xx client errors)
2. When operations are not idempotent
3. When retries would overload an already struggling service
4. When you don't have timeouts (infinite retry)

**Real-World Use Cases:**

- **Database Connections:** Retry on deadlock or connection timeout
- **Network Requests:** Retry on packet loss
- **API Calls:** Retry on 5xx server errors
- **Message Processing:** Retry on processing failures
- **External Services:** Handle temporary outages

**Advantages**

1. **Increased Reliability:** Transient failures become invisible
2. **Better User Experience:** Fewer errors seen by users
3. **Self-Healing:** System recovers from temporary issues
4. **Simple Implementation:** Relatively easy to add
5. **Reduced Support Calls:** Fewer user-reported errors

**Disadvantages**

1. **Increased Latency:** Retries add delay
2. **Resource Usage:** Retries consume resources
3. **Amplification:** Can amplify load on failing services
4. **Idempotency Required:** Must ensure duplicate operations are safe
5. **Complex State:** Need to track retry counts

**Comparison with Other Patterns**

| Pattern | Purpose | Difference |
|---------|---------|------------|
| Retry | Transient failures | Attempts again |
| Circuit Breaker | Repeated failures | Stops attempts |
| Timeout | Bound wait time | Prevents waiting |
| Fallback | Alternative response | Provides backup |

**Best Practices**

1. **Use Exponential Backoff:** Prevents overload during recovery
2. **Add Jitter:** Randomizes retry times, prevents thundering herd
3. **Set Max Retries:** Avoid infinite retries
4. **Only Retry Transient Failures:** Not 4xx errors
5. **Implement Idempotency:** Use idempotency keys for non-idempotent operations
6. **Monitor Retry Rates:** High retry rates indicate problems
7. **Combine with Circuit Breaker:** Stop retrying when circuit is open

## Chapter 7: Bulkhead Pattern

**Detailed Explanation**

The Bulkhead pattern isolates elements of an application into separate pools so that if one fails, the others continue to function. Named after ship bulkheads—watertight compartments that prevent sinking if one compartment is breached.

**Understanding the Problem**

In distributed systems, a single service handles multiple types of requests:
- Critical (checkout)
- Non-critical (recommendations)
- Different tenants
- Different downstream services

Without isolation, a problem in one area affects all others:
- A slow endpoint consumes all threads
- One tenant's heavy usage degrades service for all
- A failing downstream service causes all requests to wait

**The Solution**

The Bulkhead pattern partitions resources into isolated pools:
- **Thread Pool Bulkhead:** Separate thread pools for different request types
- **Connection Pool Bulkhead:** Separate connection pools for different downstream services
- **Semaphore Bulkhead:** Limit concurrent requests without separate threads
- **Tenant-Based Bulkhead:** Separate resources per tenant

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

// Thread Pool Bulkhead
public class ThreadPoolBulkhead {
    private final ExecutorService criticalPool;
    private final ExecutorService nonCriticalPool;
    private final ExecutorService adminPool;
    
    public ThreadPoolBulkhead() {
        this.criticalPool = Executors.newFixedThreadPool(10);
        this.nonCriticalPool = Executors.newFixedThreadPool(5);
        this.adminPool = Executors.newFixedThreadPool(2);
    }
    
    public CompletableFuture<String> executeCritical(String task) {
        return CompletableFuture.supplyAsync(() -> {
            // Critical logic
            return process(task);
        }, criticalPool);
    }
    
    public CompletableFuture<String> executeNonCritical(String task) {
        return CompletableFuture.supplyAsync(() -> {
            // Non-critical logic (recommendations, analytics)
            return process(task);
        }, nonCriticalPool);
    }
    
    private String process(String task) {
        // Simulate work
        try { Thread.sleep(100); } catch (InterruptedException e) {}
        return "Processed: " + task;
    }
}

// Semaphore Bulkhead
public class SemaphoreBulkhead {
    private final Semaphore permits;
    private final int maxConcurrent;
    
    public SemaphoreBulkhead(int maxConcurrent) {
        this.maxConcurrent = maxConcurrent;
        this.permits = new Semaphore(maxConcurrent);
    }
    
    public <T> T execute(Supplier<T> operation) throws Exception {
        if (!permits.tryAcquire(100, TimeUnit.MILLISECONDS)) {
            throw new BulkheadException("Bulkhead full, cannot process");
        }
        
        try {
            return operation.get();
        } finally {
            permits.release();
        }
    }
}

// Connection Pool Bulkhead
public class ConnectionPoolBulkhead {
    private final Map<String, HikariDataSource> dataSources = new ConcurrentHashMap<>();
    
    public Connection getConnection(String database) throws SQLException {
        HikariDataSource ds = dataSources.computeIfAbsent(database, 
            key -> createDataSource(key, getPoolSize(key)));
        
        return ds.getConnection();
    }
    
    private int getPoolSize(String database) {
        // Different pool sizes for different databases
        switch(database) {
            case "primary": return 20;
            case "secondary": return 10;
            case "analytics": return 5;
            default: return 10;
        }
    }
    
    private HikariDataSource createDataSource(String name, int poolSize) {
        HikariConfig config = new HikariConfig();
        config.setMaximumPoolSize(poolSize);
        config.setPoolName(name + "-pool");
        // other config...
        return new HikariDataSource(config);
    }
}
```

**Suitable Situations:**

1. When you have multiple types of requests with different priorities
2. When you have multiple tenants and need isolation
3. When you have downstream services with different reliability
4. When you need to ensure critical functions continue during partial failures
5. When you want to limit blast radius of failures

**Real-World Use Cases:**

- **API Gateway:** Separate pools for different API endpoints
- **Microservices:** Isolation between different services
- **Database Access:** Separate connection pools for different databases
- **Multi-Tenant SaaS:** Resource isolation per tenant
- **Priority Queues:** Critical vs non-critical tasks

**Advantages**

1. **Fault Isolation:** Problems contained within one compartment
2. **Continued Operation:** Critical functions remain available
3. **Resource Guarantees:** Each type gets guaranteed resources
4. **Noisy Neighbor Prevention:** One tenant can't starve others
5. **Graceful Degradation:** System degrades partially, not completely

**Disadvantages**

1. **Resource Inefficiency:** Reserved resources may be idle
2. **Complexity:** More pools to configure and manage
3. **Tuning Difficulty:** Sizing pools correctly is hard
4. **Configuration Overhead:** Each endpoint/tenant needs configuration
5. **Monitoring Complexity:** Need to monitor each pool separately

**Comparison with Other Patterns**

| Pattern | Purpose | Difference |
|---------|---------|------------|
| Bulkhead | Isolate resources | Partition resources |
| Circuit Breaker | Stop failing calls | Trip on failures |
| Retry | Retry transient failures | Attempts again |

**Best Practices**

1. **Size Pools Appropriately:** Consider expected load per pool
2. **Monitor Pool Usage:** Track utilization, queue size
3. **Set Timeouts:** Prevent threads from hanging forever
4. **Test Failure Scenarios:** Verify isolation works
5. **Combine with Circuit Breaker:** Use both for comprehensive resilience

## Chapter 8: Health Check Pattern

**Detailed Explanation**

The Health Check pattern exposes an endpoint (e.g., `/health`) that returns the health status of a service. It allows monitoring systems, load balancers, and orchestrators to know if a service is running and able to handle requests.

**Understanding the Problem**

In distributed systems, services can fail in many ways:
- Process crash (not running)
- Hung process (running but not responding)
- Dependency failure (database down)
- Resource exhaustion (out of memory)
- Configuration error (started but misconfigured)

Without health checks, you don't know if a service is actually able to handle requests. A service might be "up" but "unhealthy."

**The Solution**

Each service exposes a health check endpoint that returns:
- **Status:** Overall health (UP, DOWN, DEGRADED)
- **Details:** Status of each dependency (database, cache, external API)
- **Version:** Service version for deployment tracking
- **Build Info:** Commit hash, build time

**Types of Health Checks**

- **Liveness:** Is the service alive? (process running)
- **Readiness:** Is the service ready to accept traffic?
- **Startup:** Is the service still starting up?

```java
import org.springframework.boot.actuate.health.*;
import org.springframework.stereotype.Component;
import java.sql.*;

@Component
public class CustomHealthIndicator implements HealthIndicator {
    
    @Autowired
    private DataSource dataSource;
    
    @Autowired
    private RedisClient redisClient;
    
    @Override
    public Health health() {
        Health.Builder builder = new Health.Builder();
        
        // Check database
        Health dbHealth = checkDatabase();
        if (dbHealth.getStatus() != Status.UP) {
            builder.down().withDetail("database", dbHealth.getDetails());
        } else {
            builder.up().withDetail("database", dbHealth.getDetails());
        }
        
        // Check Redis
        Health redisHealth = checkRedis();
        if (redisHealth.getStatus() != Status.UP) {
            builder.down().withDetail("redis", redisHealth.getDetails());
        } else {
            builder.withDetail("redis", redisHealth.getDetails());
        }
        
        // Check disk space
        Health diskHealth = checkDiskSpace();
        if (diskHealth.getStatus() == Status.DOWN) {
            builder.down();
        } else if (diskHealth.getStatus() == Status.UNKNOWN) {
            builder.unknown();
        }
        builder.withDetail("disk", diskHealth.getDetails());
        
        return builder.build();
    }
    
    private Health checkDatabase() {
        try (Connection conn = dataSource.getConnection()) {
            boolean valid = conn.isValid(5);
            if (valid) {
                return Health.up()
                    .withDetail("latency", getLatency())
                    .build();
            }
            return Health.down().withDetail("error", "Invalid connection").build();
        } catch (SQLException e) {
            return Health.down(e).build();
        }
    }
    
    private Health checkRedis() {
        try {
            String pong = redisClient.ping();
            if ("PONG".equals(pong)) {
                return Health.up().build();
            }
            return Health.down().withDetail("response", pong).build();
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
    
    private Health checkDiskSpace() {
        File file = new File("/");
        long free = file.getFreeSpace();
        long total = file.getTotalSpace();
        long used = total - free;
        double percentUsed = (double) used / total * 100;
        
        if (percentUsed > 90) {
            return Health.down()
                .withDetail("free", free)
                .withDetail("percentUsed", percentUsed)
                .build();
        } else if (percentUsed > 80) {
            return Health.unknown()
                .withDetail("free", free)
                .withDetail("percentUsed", percentUsed)
                .build();
        }
        return Health.up().withDetail("free", free).build();
    }
}
```

**When to Use Health Check Pattern**

**Suitable Situations:**

1. In every service (essential)
2. When using container orchestration (Kubernetes)
3. When using load balancers that need to know healthy instances
4. When you have monitoring systems that need to alert on failures
5. When you have dependencies that can fail independently

**Real-World Use Cases:**

- **Kubernetes:** Liveness and readiness probes
- **Load Balancers:** AWS ELB health checks
- **Service Mesh:** Istio health checks
- **Monitoring:** Prometheus exporter
- **Orchestration:** Health-based routing

**Advantages**

1. **Automated Recovery:** Orchestration can restart unhealthy instances
2. **Traffic Management:** Load balancers stop sending traffic to unhealthy instances
3. **Early Warning:** Monitoring can alert before total failure
4. **Dependency Visibility:** Know which dependencies are causing problems
5. **Deployment Safety:** Ensure new versions are healthy before receiving traffic

**Disadvantages**

1. **Implementation Effort:** Need to add health checks to each service
2. **Potential Overhead:** Health checks add load to dependencies
3. **False Negatives:** Aggressive checks might mark service unhealthy unnecessarily
4. **Security:** Health endpoint must be secured appropriately
5. **Cascading Checks:** Health checks that depend on other services can cause cascading failures

**Best Practices**

1. **Separate Liveness and Readiness:** Different probes for different purposes
2. **Lightweight Checks:** Health checks should be fast (< 1s)
3. **Cache Results:** Don't check dependencies on every request
4. **Set Timeouts:** Don't wait forever for dependencies
5. **Include Version Info:** Help with deployment tracking
6. **Secure Endpoints:** Don't expose sensitive data

## Chapter 9: Timeout Pattern

**Detailed Explanation**

The Timeout pattern sets a maximum time to wait for an operation to complete. If the operation doesn't complete within the timeout, it's considered failed, and the caller can proceed.

**Understanding the Problem**

In distributed systems, services can hang for many reasons:
- Network problems
- Deadlocks
- Resource exhaustion
- Bugs causing infinite loops
- Downstream service failures

Without timeouts, a client can wait forever. This leads to:
- **Thread Exhaustion:** Threads blocked indefinitely
- **Resource Leaks:** Connections, memory held indefinitely
- **Cascading Failures:** Waiting clients accumulate
- **Poor User Experience:** Users wait forever

**The Solution**

The Timeout pattern sets time limits on operations:
- **Connection Timeout:** Time to establish connection
- **Read Timeout:** Time to receive response after connection
- **Request Timeout:** Total time for complete request

When timeout expires, the operation is considered failed, and the client can:
- Throw an exception
- Return a fallback value
- Retry (if appropriate)
- Log the timeout

**Implementation Example**

```java
import java.net.http.*;
import java.time.Duration;
import java.util.concurrent.*;

public class TimeoutHandler {
    
    // HTTP Client with timeouts
    public String callWithTimeouts(String url) {
        HttpClient client = HttpClient.newBuilder()
            .connectTimeout(Duration.ofMillis(500))  // connection timeout
            .build();
        
        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create(url))
            .timeout(Duration.ofSeconds(2))  // request timeout
            .build();
        
        try {
            HttpResponse<String> response = client.send(
                request, HttpResponse.BodyHandlers.ofString());
            return response.body();
        } catch (HttpTimeoutException e) {
            System.err.println("Request timed out");
            return null;
        } catch (Exception e) {
            return null;
        }
    }
    
    // CompletableFuture with timeout
    public CompletableFuture<String> asyncCallWithTimeout(String url) {
        CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> 
            callWithTimeouts(url));
        
        return future.orTimeout(3, TimeUnit.SECONDS)
            .exceptionally(throwable -> {
                if (throwable instanceof TimeoutException) {
                    return "Timeout fallback";
                }
                return null;
            });
    }
    
    // Database query with timeout
    public ResultSet queryWithTimeout(String sql, int timeoutSeconds) 
            throws SQLException {
        PreparedStatement stmt = connection.prepareStatement(sql);
        stmt.setQueryTimeout(timeoutSeconds);
        return stmt.executeQuery();
    }
    
    // Custom timeout using ScheduledExecutorService
    public <T> T executeWithTimeout(Supplier<T> operation, 
                                     long timeout, TimeUnit unit) 
            throws TimeoutException, ExecutionException {
        
        ExecutorService executor = Executors.newSingleThreadExecutor();
        Future<T> future = executor.submit(operation::get);
        
        try {
            return future.get(timeout, unit);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(e);
        } catch (TimeoutException e) {
            future.cancel(true);
            throw e;
        } catch (ExecutionException e) {
            throw e;
        } finally {
            executor.shutdownNow();
        }
    }
}
```

**When to Use Timeout Pattern**

**Suitable Situations:**

1. In every distributed interaction (essential)
2. When calling external services
3. When making database calls
4. When performing any I/O operation
5. When you have any risk of hanging operations

**Real-World Use Cases:**

- **HTTP Clients:** Set connection and read timeouts
- **Database Queries:** Set query timeout
- **RPC Calls:** Set deadline
- **Message Queues:** Set receive timeout
- **File Operations:** Set read/write timeout

**Advantages**

1. **Resource Protection:** Prevents resource exhaustion
2. **Responsiveness:** System remains responsive even when dependencies hang
3. **Failure Detection:** Know when things are not working
4. **Cascading Failure Prevention:** Stops failures from spreading
5. **Bounded Wait Times:** Users don't wait forever

**Disadvantages**

1. **Choosing Timeouts:** Hard to choose the right value
2. **False Timeouts:** Might timeout operations that would have succeeded
3. **Complexity:** Need to handle timeout errors
4. **Performance Impact:** Too short timeouts cause unnecessary failures
5. **No One-Size-Fits-All:** Different operations need different timeouts

**Best Practices**

1. **Set Timeouts Everywhere:** Database, HTTP, RPC, everything
2. **Use Different Timeouts:** Connection vs read vs total
3. **Monitor Timeout Rates:** Track how often timeouts occur
4. **Tune Based on SLAs:** Timeouts should be less than your SLA
5. **Consider Network Latency:** Account for normal network delays
6. **Combine with Retry:** Retry after timeout for transient issues

## Chapter 10: Blue-Green Deployment

**Detailed Explanation**

Blue-Green Deployment reduces downtime and risk by running two identical production environments. Only one environment receives live traffic at a time, allowing instant rollback if problems occur.

**Understanding the Problem**

Deploying new versions always carries risk:
- **Downtime:** Traditional deployments require taking the app offline
- **Rollback Difficulty:** If something goes wrong, rolling back is slow
- **Testing Gap:** Can't fully test in production before cutover
- **User Impact:** Users see errors during deployment

**The Solution**

Blue-Green Deployment maintains two environments:
- **Blue:** Current production environment (live traffic)
- **Green:** New version (staged, tested)

When Green is ready, you switch traffic from Blue to Green. If problems occur, you switch back to Blue.

**When to Use Blue-Green Deployment**

**Suitable Situations:**

1. When you need zero-downtime deployments
2. When you have the infrastructure to run two environments
3. When you want to reduce deployment risk
4. When you need quick rollback capability
5. When you have stateless applications or can handle database changes

**Real-World Use Cases:**

- **Web Applications:** Zero-downtime feature releases
- **API Services:** Safe rollout of API changes
- **Microservices:** Independent service deployment
- **Mobile Backends:** Versioned API endpoints
- **SaaS Platforms:** Continuous deployment

**Advantages**

1. **Zero Downtime:** No interruption during switch
2. **Instant Rollback:** Switch back if problems occur
3. **Full Testing:** Green environment can be fully tested
4. **Reduced Risk:** Problems caught before full rollout
5. **Simple Mental Model:** Easy to understand

**Disadvantages**

1. **Double Infrastructure:** Need two production environments
2. **Database Challenges:** Schema changes must be compatible
3. **Stateful Services:** Harder with stateful services
4. **Cost:** Double the resources (at least during transition)
5. **Complexity:** More complex than rolling update

**Database Considerations**

For Blue-Green to work with databases:
- Schema changes must be backward-compatible
- Old version must work with new schema
- Use feature flags to enable new features after switch

## Chapter 11: Canary Deployment

**Detailed Explanation**

Canary Deployment gradually rolls out a new version to a small subset of users first. If it works well, you gradually increase the percentage. The name comes from "canary in a coal mine"—if there's a problem, only a few users are affected.

**Understanding the Problem**

Blue-Green switches all traffic at once. While better than downtime, it still has risks:
- **All-or-Nothing:** If something is wrong, all users are affected
- **Limited Testing:** Can't test with real production load
- **Gradual Exposure:** Some problems only appear with scale

**The Solution**

Canary Deployment:
1. **Start Small:** Route a small percentage to new version (1-5%)
2. **Monitor:** Watch metrics, errors, performance
3. **Gradual Increase:** If healthy, increase percentage
4. **Rollback:** If problems, route traffic back
5. **Full Rollout:** Eventually route all traffic to new version

**When to Use Canary Deployment**

**Suitable Situations:**

1. When you want to minimize risk of new releases
2. When you have monitoring to detect problems
3. When you can route traffic based on percentages
4. When you want to test with real production load
5. When you're deploying significant changes

**Real-World Use Cases:**

- **Large-Scale Systems:** Netflix, Facebook, Google
- **Microservices:** Gradual service upgrades
- **Feature Rollouts:** New features to small user groups
- **A/B Testing:** Compare versions
- **Performance Testing:** Test under real load

**Advantages**

1. **Minimized Risk:** Only small percentage affected
2. **Real-World Testing:** Tests with actual production traffic
3. **Gradual Rollout:** Can stop if problems detected
4. **Performance Validation:** See real performance before full rollout
5. **A/B Testing Possibility:** Can compare behavior

**Disadvantages**

1. **Complexity:** More complex than blue-green
2. **Longer Rollout:** Takes time to gradually increase
3. **Monitoring Required:** Need good monitoring to detect issues
4. **State Management:** Harder with stateful services
5. **User Experience:** Some users see new version, some old

**Comparison with Blue-Green**

| Risk | All users at once | Small subset first |

| Complexity | Moderate | Higher |
| Rollback | Instant | Instant (stop traffic) |
| Testing | Pre-production | Production (small) |
| Use case | Low-risk changes | Higher-risk changes |

## Chapter 12: Feature Toggles (Flags)

**Detailed Explanation**

Feature Toggles (also called Feature Flags) allow you to enable or disable features at runtime without deploying new code. They separate deployment from release, enabling safer, more controlled rollouts.

**Understanding the Problem**

Deploying code with new features is risky because:
- Code is released with new features immediately
- Can't test new features in production safely
- Hard to roll back if issues occur
- Can't target specific users for testing

**The Solution**

Feature Toggles wrap new functionality in conditional checks:
- **Release Toggles:** Control rollout of new features
- **Experiment Toggles:** A/B testing, user segmentation
- **Ops Toggles:** Operational controls (kill switches)
- **Permission Toggles:** Per-user feature access

**Types of Feature Toggles**

| Type | Purpose | Lifetime |
|------|---------|----------|
| Release Toggle | Separate deploy from release | Days to weeks |
| Experiment Toggle | A/B testing | Weeks to months |
| Ops Toggle | Kill switches, circuit breakers | Permanent |
| Permission Toggle | Beta, early access | Permanent |

```java
import java.util.*;
import java.util.concurrent.*;

public class FeatureFlags {
    private final Map<String, Boolean> staticFlags = new ConcurrentHashMap<>();
    private final Map<String, Function<UserContext, Boolean>> dynamicFlags = new ConcurrentHashMap<>();
    
    public FeatureFlags() {
        // Initialize default flags
        staticFlags.put("new-checkout", false);
        staticFlags.put("new-recommendations", false);
    }
    
    public void enable(String flag) {
        staticFlags.put(flag, true);
    }
    
    public void disable(String flag) {
        staticFlags.put(flag, false);
    }
    
    public void enableForPercentage(String flag, int percentage) {
        dynamicFlags.put(flag, context -> {
            // Consistent hashing based on user ID
            int hash = Math.abs(context.getUserId().hashCode() % 100);
            return hash < percentage;
        });
    }
    
    public void enableForUsers(String flag, List<String> userIds) {
        Set<String> userSet = new HashSet<>(userIds);
        dynamicFlags.put(flag, context -> userSet.contains(context.getUserId()));
    }
    
    public boolean isEnabled(String flag) {
        return isEnabled(flag, null);
    }
    
    public boolean isEnabled(String flag, UserContext context) {
        // Check dynamic flags first
        Function<UserContext, Boolean> dynamic = dynamicFlags.get(flag);
        if (dynamic != null && context != null) {
            return dynamic.apply(context);
        }
        
        // Fall back to static
        return staticFlags.getOrDefault(flag, false);
    }
    
    // User context for targeted rollouts
    public static class UserContext {
        private final String userId;
        private final String email;
        private final String region;
        
        public UserContext(String userId, String email, String region) {
            this.userId = userId;
            this.email = email;
            this.region = region;
        }
        
        public String getUserId() { return userId; }
        public String getEmail() { return email; }
        public String getRegion() { return region; }
    }
}

// Usage in code
public class CheckoutService {
    private final FeatureFlags featureFlags;
    
    public CheckoutResponse checkout(CheckoutRequest request) {
        UserContext user = request.getUser();
        
        if (featureFlags.isEnabled("new-checkout", user)) {
            return newCheckoutFlow(request);
        } else {
            return oldCheckoutFlow(request);
        }
    }
}
```

**When to Use Feature Toggles**

**Suitable Situations:**

1. When you want to separate deployment from release
2. When you need to test features in production
3. When you want gradual rollouts (canary for features)
4. When you need kill switches for problematic features
5. For A/B testing and experiments

**Real-World Use Cases:**

- **E-commerce:** Gradual checkout flow rollout
- **SaaS:** Beta features for select customers
- **Mobile Apps:** Remote feature enable/disable
- **Microservices:** Circuit breaking via toggle
- **A/B Testing:** Experiment with variants

**Advantages**

1. **Safe Rollouts:** Release to small audience first
2. **Instant Rollback:** Disable problematic features instantly
3. **Separate Deploy from Release:** Deploy anytime, release when ready
4. **A/B Testing:** Compare different versions
5. **Continuous Delivery:** Deploy frequently with confidence

**Disadvantages**

1. **Technical Debt:** Toggles need to be cleaned up
2. **Complexity:** Code becomes more complex
3. **Testing Overhead:** Need to test both on/off states
4. **Performance:** Flag evaluation overhead
5. **Infrastructure:** Need flag management service

**Best Practices**

1. **Remove Old Toggles:** Clean up after full rollout
2. **Short Lifespan:** Release toggles should be temporary
3. **Test Both States:** Ensure code works with flag on and off
4. **Monitor Toggle Usage:** Track flag evaluations
5. **Use Type-Safe Toggles:** Avoid stringly-typed flags

## Chapter 13: Sidecar Pattern

**Detailed Explanation**

The Sidecar pattern deploys auxiliary components alongside the main application container. Sidecars provide supporting features like logging, monitoring, configuration, and service mesh proxies without modifying the main application.

**Understanding the Problem**

Applications need many supporting functions:
- Logging agents
- Metrics collectors
- Configuration management
- Service discovery
- Security proxies

Embedding these in the app causes:
- Code bloat
- Language constraints
- Upgrade difficulties
- Cross-cutting concerns mixing

**The Solution**

Sidecar runs in separate container/process:
- **Co-located:** Runs on same host as main app
- **Shared Lifecycle:** Deployed and scaled together
- **Local Communication:** Communicates via localhost
- **Language-Agnostic:** Can be written in any language
- **Independent Upgrades:** Can be updated separately

2. When you want language-agnostic infrastructure
3. When you need independent upgrades
4. For service mesh implementations
5. For logging and monitoring agents

**Real-World Use Cases:**

- **Kubernetes:** Sidecar containers for logging, monitoring
- **Service Mesh:** Envoy sidecar for service-to-service communication
- **Logging:** Fluentd sidecar for log shipping
- **Configuration:** Consul Template for dynamic config
- **Security:** OAuth2 proxy sidecar for authentication

**Advantages**

1. **Separation of Concerns:** Business logic separate from infrastructure
2. **Language-Agnostic:** Can use different languages
3. **Independent Upgrades:** Sidecar can be updated separately

## Chapter 14: Service Mesh

**Detailed Explanation**

A Service Mesh is a dedicated infrastructure layer for handling service-to-service communication. It provides observability, security, and reliability features without requiring changes to application code.

**Understanding the Problem**

Microservices need many features:
- Service discovery
- Load balancing
- Circuit breaking
- Retries
- Timeouts
- Authentication (mTLS)
- Observability (tracing, metrics)

Implementing these in each service leads to:
- Code duplication
- Language lock-in
- Maintenance burden
- Inconsistent implementations

**The Solution**

Service Mesh provides a sidecar proxy (like Envoy) for each service. Proxies handle all network communication, providing:
- **Data Plane:** Sidecar proxies that intercept traffic
- **Control Plane:** Manages configuration and policies
- **Observability:** Metrics, logs, traces automatically
- **Security:** mTLS encryption between services
- **Resilience:** Circuit breakers, retries, timeouts

**When to Use Service Mesh**

2. When you need consistent security across services (mTLS)
3. When you need advanced traffic management (canary, A/B)
4. When you want to offload resilience patterns from application
5. When you need deep observability across all services

**Real-World Use Cases:**

- **Large Microservices Deployments:** 100+ services
- **Security-Critical Applications:** mTLS enforcement
- **Multi-Cloud Deployments:** Consistent networking
- **Platform Teams:** Providing common infrastructure
- **Legacy Modernization:** Adding features without code changes

**Advantages**

2. **Consistent Policies:** Same features across all services

## Chapter 15: Gateway Routing / API Gateway

**Detailed Explanation**

The API Gateway pattern provides a single entry point for all client requests to a microservices-based application. It handles routing, authentication, rate limiting, and response aggregation.

**Understanding the Problem**

Microservices have many endpoints. Without a gateway, clients need to:
- Know multiple service locations
- Handle authentication for each service
- Make multiple requests for one page
- Deal with different protocols
- Handle errors and retries

**The Solution**

API Gateway provides:
- **Single Entry Point:** One URL for all services
- **Routing:** Route requests to appropriate services
- **Authentication:** Centralized authentication
- **Aggregation:** Combine multiple service responses
- **Cross-cutting Concerns:** Rate limiting, caching, logging

## Chapter 16: API Composition

**Detailed Explanation**

The API Composition pattern aggregates data from multiple services to fulfill a single client request. It reduces client complexity and round trips by combining multiple service calls.

**Understanding the Problem**

A single client request often needs data from multiple services:
- Order details: Order Service + Customer Service + Product Service
- User profile: User Service + Profile Service + Settings Service

Without composition, the client must:
- Make multiple network calls
- Handle failures from each call
- Combine results manually
- Deal with different data formats

**The Solution**

API Composition introduces a service (often part of API Gateway) that:
- Receives the client request
- Makes calls to required services (parallel or sequential)
- Aggregates responses
- Returns combined result to client

```java
@RestController
public class OrderCompositionController {
    
    @Autowired
    private OrderServiceClient orderClient;
    
    @Autowired
    private CustomerServiceClient customerClient;
    
    @Autowired
    private ProductServiceClient productClient;
    
    @GetMapping("/api/composite/orders/{orderId}")
    public CompletableFuture<OrderComposite> getOrderComposite(
            @PathVariable String orderId) {
        
        // Fetch order details
        CompletableFuture<Order> orderFuture = 
            CompletableFuture.supplyAsync(() -> orderClient.getOrder(orderId));
        
        // After order is fetched, fetch customer and products in parallel
        return orderFuture.thenCompose(order -> {
            CompletableFuture<Customer> customerFuture = 
                CompletableFuture.supplyAsync(() -> 
                    customerClient.getCustomer(order.getCustomerId()));
            
            CompletableFuture<List<Product>> productsFuture = 
                CompletableFuture.supplyAsync(() -> 
                    productClient.getProducts(order.getProductIds()));
            
            // Combine all results
            return CompletableFuture.allOf(customerFuture, productsFuture)
                .thenApply(v -> {
                    OrderComposite composite = new OrderComposite();
                    composite.setOrder(order);
                    composite.setCustomer(customerFuture.join());
                    composite.setProducts(productsFuture.join());
                    return composite;
                });
        });
    }
}
```

## Chapter 17: Load Balancing

**Detailed Explanation**

Load Balancing distributes incoming traffic across multiple servers to ensure no single server is overwhelmed, improving reliability, availability, and scalability.

**Understanding the Problem**

A single server has limits:
- Can only handle so many concurrent connections
- Single point of failure
- Can't scale beyond hardware limits

**The Solution**

Load Balancer sits between clients and servers:
- **Health Checks:** Only sends traffic to healthy servers
- **Distribution Algorithm:** Determines how to distribute requests
- **Scalability:** Add more servers behind load balancer
- **Fault Tolerance:** Removes unhealthy servers

**Load Balancing Algorithms**

| Algorithm | Description | Use Case |
|-----------|-------------|----------|
| Round Robin | Rotates through servers | Simple, even distribution |
| Least Connections | Sends to server with fewest connections | Varying request durations |
| Least Response Time | Sends to fastest responding server | Performance-sensitive |
| IP Hash | Consistent hashing based on client IP | Session persistence |
| Random | Random selection | Simple, good for many servers |

## Chapter 18: Leader Election

**Detailed Explanation**

Leader Election is a pattern where one node in a cluster is elected as the leader to coordinate work, while other nodes are followers. If the leader fails, a new leader is elected automatically.

**Understanding the Problem**

In distributed systems, some tasks require coordination:
- Scheduling jobs
- Coordinating writes
- Managing shared resources
- Ensuring only one node performs certain work

Without leader election, nodes may conflict or duplicate work.

**The Solution**

Leader Election ensures:
- **Single Leader:** Only one node is leader at a time
- **Automatic Failover:** If leader fails, new leader elected
- **Fencing:** Ensures old leader doesn't cause issues
- **Lease:** Leader holds lease for limited time, renews periodically

**Election Algorithms**

| Algorithm | Description | Example |
|-----------|-------------|---------|
| Bully Algorithm | Highest ID node wins | Simple, can be unstable |
| Paxos | Consensus-based election | ZooKeeper, etcd |
| Raft | Leader election with logs | etcd, Consul |
| Lamport Timestamps | Logical clocks | Distributed systems |

```java
                    }
                }
```

## Chapter 19: Distributed Cache

**Detailed Explanation**

A Distributed Cache is a cache shared across multiple application instances. It stores frequently accessed data in memory, reducing database load and improving response times.

**Understanding the Problem**

Database access is slow and expensive:
- Each query takes milliseconds
- High load can overwhelm database
- Cannot scale as fast as application
- Network latency adds overhead

**The Solution**

Distributed Cache provides:
- **In-Memory Storage:** Fast access (microseconds)
- **Shared Across Instances:** All app instances share cache
- **Automatic Eviction:** Removes old/stale data
- **Replication:** Data replicated for availability
- **Partitioning:** Data distributed across nodes

| Read-Through | Cache reads from DB on miss | Simple reads |

```java
@Service
public class CachedUserService {
    
    @Autowired
    private RedisTemplate<String, User> redisTemplate;
    
    @Autowired
    private UserRepository userRepository;
    
    private static final String CACHE_KEY_PREFIX = "user:";
    private static final int TTL_SECONDS = 300; // 5 minutes
    
    public User getUser(String userId) {
        // Try cache first
        String cacheKey = CACHE_KEY_PREFIX + userId;
        User cachedUser = redisTemplate.opsForValue().get(cacheKey);
        
        if (cachedUser != null) {
            return cachedUser;
        }
        
        // Cache miss - get from database
        User user = userRepository.findById(userId)
            .orElseThrow(() -> new UserNotFoundException(userId));
        
        // Store in cache
        redisTemplate.opsForValue().set(cacheKey, user, TTL_SECONDS, TimeUnit.SECONDS);
        
        return user;
    }
    
    public void updateUser(User user) {
        // Update database
        userRepository.save(user);
        
        // Invalidate cache
        String cacheKey = CACHE_KEY_PREFIX + user.getId();
        redisTemplate.delete(cacheKey);
    }
}
```

## Chapter 20: Sharding

**Detailed Explanation**

Sharding (horizontal partitioning) splits data across multiple databases. Each shard contains a subset of the data, allowing horizontal scaling beyond single-database limits.

**Understanding the Problem**

Single database has limits:
- Storage capacity
- Write throughput
- Connection limits
- Query performance

**The Solution**

Sharding distributes data across multiple databases:
- **Shard Key:** Field used to distribute data
- **Shard:** Independent database instance
- **Partitioning:** Data split by shard key range or hash
- **Scalable:** Add shards to increase capacity

**Sharding Strategies**

| Strategy | Description | Example |
|----------|-------------|---------|
| Range-Based | Split by value ranges | user_id 1-1000 in shard 1 |
| Hash-Based | Hash of key modulo N | hash(user_id) % 4 |
| Directory-Based | Lookup table | user_id → shard mapping |
| Geo-Based | By geographic region | US users in shard A |

```java
public class ShardRouter {

    public DataSource getShardForUser(String userId) {
        // Hash-based sharding
        int shardId = Math.abs(userId.hashCode()) % numberOfShards;
        return shardDataSources.get(shardId);
    }
    
    public DataSource getShardForOrder(String orderId) {
        // Range-based sharding (orders by date)
        // Example: orders from 2024 in shard 0, 2023 in shard 1, etc.
        return shardDataSources.get(extractYear(orderId) % numberOfShards);
    }
    
    // For queries without shard key
    public List<DataSource> getAllShards() {
        return new ArrayList<>(shardDataSources.values());
    }
}

// Repository using shard router
@Repository
public class UserShardedRepository {
    
    @Autowired
    private ShardRouter shardRouter;
    
    public User findById(String userId) {
        DataSource ds = shardRouter.getShardForUser(userId);
        // Use DataSource to query user
        return queryUser(ds, userId);
    }
    
    public List<User> findAll() {
        // Query all shards and combine results
        List<User> allUsers = new ArrayList<>();
        for (DataSource ds : shardRouter.getAllShards()) {
            allUsers.addAll(queryAllUsers(ds));
        }
        return allUsers;
    }
}
```

**When to Use Sharding**

**Suitable Situations:**

1. When data is too large for a single database
2. When write throughput exceeds single database capacity
3. When you need linear scalability
4. When data can be partitioned by a natural key
5. For multi-tenant applications

**Real-World Use Cases:**

- **Large-Scale SaaS:** Shard per customer
- **Social Media:** User data partitioned by user ID
- **E-commerce:** Order data by region or time
- **Gaming:** Player data by region
- **Analytics:** Time-series data by date

**Advantages**

1. **Scalability:** Add shards to scale
2. **Performance:** Each shard handles less load
3. **Availability:** Shard failures affect only subset
4. **Parallelism:** Queries can run in parallel
5. **Cost:** Use smaller, cheaper hardware

**Disadvantages**

1. **Complexity:** Application must handle sharding
2. **Cross-Shard Queries:** Difficult and slow
3. **Rebalancing:** Adding shards requires moving data
4. **Shard Key Selection:** Hard to choose good key
5. **Transactions:** No ACID across shards

## Chapter 21: CQRS (Command Query Responsibility Segregation)

**Detailed Explanation**

CQRS separates the operations that read data (queries) from the operations that write data (commands). Different models optimize for each operation, enabling independent scaling and optimization.

**Understanding the Problem**

Traditional CRUD uses the same model for reads and writes, causing:
- Complex domain logic mixed with query concerns
- Performance conflicts (reads vs writes)
- Scalability challenges (can't scale reads independently)
- Security issues (same permissions for read/write)

**The Solution**

CQRS separates:
- **Command Side:** Handles updates (create, update, delete)
- **Query Side:** Handles reads (queries)
- **Models:** Different models for each side
- **Data Stores:** Can use separate databases
- **Eventual Consistency:** Reads may lag behind writes

2. When you have complex domain logic on the write side
3. When you need different security for reads and writes
4. When you want to scale reads and writes independently
5. When you need multiple read models for different contexts

**Real-World Use Cases:**

- **E-commerce:** Product catalog (many reads, few writes)
- **Banking:** Account transactions (complex write logic)
- **Collaboration Tools:** Document editing (collaborative writes)
- **Analytics:** Read-only reports from event streams
- **High-Traffic APIs:** Read-heavy with caching

**Advantages**

1. **Independent Scaling:** Scale reads and writes separately
2. **Optimized Models:** Best model for each operation
3. **Performance:** Read queries can be highly optimized
4. **Security:** Different permissions per side
5. **Flexibility:** Can use different technologies per side

**Disadvantages**

1. **Complexity:** More complex than CRUD
2. **Consistency:** Eventual consistency between sides
3. **Development Overhead:** Need to maintain two models
4. **Synchronization:** Need to keep sides in sync
5. **Learning Curve:** Team must understand the pattern

## Chapter 22: Health Check (Extended)

**Detailed Explanation**

The Health Check pattern exposes an endpoint that returns the health status of a service, allowing monitoring systems, load balancers, and orchestrators to know if the service is able to handle requests.

**Health Check Types**

| Type | Purpose | Example |
|------|---------|---------|
| Liveness | Is the process alive? | `/live` endpoint |
| Readiness | Is service ready for traffic? | `/ready` endpoint |
| Startup | Is service still starting? | `/startup` endpoint |

**Implementation Example**

```java
@RestController
public class HealthController {
    
    @Autowired
    private DataSource dataSource;
    
    @Autowired
    private RedisClient redisClient;
    
    @GetMapping("/health")
    public HealthResponse health() {
        HealthResponse response = new HealthResponse();
        response.setStatus("UP");
        
        // Check database
        HealthCheck dbHealth = checkDatabase();
        response.addCheck("database", dbHealth);
        if (dbHealth.getStatus() != "UP") {
            response.setStatus("DEGRADED");
        }
        
        // Check Redis
        HealthCheck redisHealth = checkRedis();
        response.addCheck("redis", redisHealth);
        if (redisHealth.getStatus() != "UP") {
            response.setStatus("DEGRADED");
        }
        
        // Check disk space
        HealthCheck diskHealth = checkDiskSpace();
        response.addCheck("disk", diskHealth);
        if (diskHealth.getStatus() == "DOWN") {
            response.setStatus("DOWN");
        }
        
        // Add version info
        response.setVersion(version);
        response.setCommit(commitHash);
        
        return response;
    }
    
    @GetMapping("/ready")
    public ResponseEntity<?> ready() {
        // Check if service is ready to accept traffic
        if (isReady()) {
            return ResponseEntity.ok().build();
        }
        return ResponseEntity.status(503).build();
    }
    
    @GetMapping("/live")
    public ResponseEntity<?> live() {
        // Simple liveness check
        return ResponseEntity.ok().build();
    }
}
```

**Best Practices**

1. **Separate Liveness and Readiness:** Different endpoints for different purposes
2. **Lightweight Checks:** Health checks should be fast (< 1s)
3. **Cache Results:** Don't check dependencies on every request
4. **Set Timeouts:** Don't wait forever for dependencies
5. **Include Version Info:** Help with deployment tracking

## Chapter 23: Rate Limiting

**Detailed Explanation**

Rate Limiting controls the rate at which operations are performed to prevent system overload, ensure fair resource distribution, and protect against abuse.

**Understanding the Problem**

Without rate limiting:
- Malicious clients can overwhelm system (DoS)
- One tenant can consume all resources
- Downstream services can be overloaded
- Costs can spike unexpectedly

**The Solution**

Rate Limiting algorithms:

| Algorithm | Description | Pros | Cons |
|-----------|-------------|------|------|
| Token Bucket | Tokens replenished at fixed rate | Smooths bursts | More complex |
| Leaky Bucket | Constant output rate | Smooth output | No bursting |
| Fixed Window | Count per time window | Simple | Boundary bursts |
| Sliding Window | Rolling time window | Accurate | More complex |

```java
public class TokenBucketRateLimiter {
    private final long capacity;
    private final long refillRate; // tokens per second
    private final AtomicLong availableTokens;
    private final AtomicLong lastRefillTime;
    
    public TokenBucketRateLimiter(long capacity, long refillRate) {
        this.capacity = capacity;
        this.refillRate = refillRate;
        this.availableTokens = new AtomicLong(capacity);
        this.lastRefillTime = new AtomicLong(System.nanoTime());
    }
    
    public boolean tryAcquire() {
        refill();
        long current = availableTokens.get();
        while (current > 0 && !availableTokens.compareAndSet(current, current - 1)) {
            current = availableTokens.get();
        }
        return current > 0;
    }
    
    private void refill() {
        long now = System.nanoTime();
        long lastRefill = lastRefillTime.get();
        long elapsed = now - lastRefill;
        
        if (elapsed > 0) {
            long tokensToAdd = elapsed * refillRate / 1_000_000_000L;
            if (tokensToAdd > 0) {
                long newTokens = Math.min(capacity, availableTokens.get() + tokensToAdd);
                availableTokens.set(newTokens);
                lastRefillTime.set(now);
            }
        }
    }
}
```

**When to Use Rate Limiting**

**Suitable Situations:**

1. For API endpoints to prevent abuse
2. To protect downstream services from overload
3. For fair resource distribution among tenants
4. To control costs in cloud environments
5. For rate-limited external services

**Real-World Use Cases:**

- **API Gateways:** Per-client rate limiting
- **Web Servers:** Prevent DDoS attacks
- **Database Proxies:** Protect databases from high load
- **Message Queues:** Control processing rates
- **Cloud Services:** AWS throttling, API Gateway

**Best Practices**

1. **Return Headers:** Include limit, remaining, reset information
2. **Exponential Backoff:** Client retry with backoff
3. **Distributed Coordination:** Use Redis for shared state
4. **Monitor:** Track rate limiting events
5. **Granular Limits:** Different limits for different clients

## Chapter 24: Distributed Tracing

**Detailed Explanation**

Distributed Tracing tracks a single request as it travels through multiple services, providing end-to-end visibility into request flows, latency, and failures.

**Understanding the Problem**

In distributed systems, a single request may traverse many services:
- API Gateway → Auth → Order → Inventory → Payment → Shipping

Without tracing, you can't:
- See the full request path
- Identify bottlenecks
- Find where errors occur
- Understand dependencies

**The Solution**

Distributed Tracing assigns a unique trace ID to each request and propagates it across services. Each service records spans (units of work) with timing information.

**Key Concepts**

- **Trace:** Complete end-to-end request path
- **Span:** Named, timed operation within a trace
- **Trace ID:** Unique identifier for entire trace
- **Span ID:** Unique identifier for each span
- **Context Propagation:** Passing trace context across service boundaries

```java
import io.opentelemetry.api.*;
import io.opentelemetry.api.trace.*;

@Service
public class OrderService {
    
    private static final Tracer tracer = 
        OpenTelemetry.getGlobalTracer("order-service");
    
    @Autowired
    private InventoryClient inventoryClient;
    
    @Autowired
    private PaymentClient paymentClient;
    
    public OrderResponse createOrder(OrderRequest request) {
        // Start span
        Span span = tracer.spanBuilder("createOrder")
            .setSpanKind(SpanKind.SERVER)
            .startSpan();
        
        try (Scope scope = span.makeCurrent()) {
            // Add attributes
            span.setAttribute("order.id", request.getId());
            span.setAttribute("order.amount", request.getAmount());
            
            // Call inventory service (trace propagated automatically)
            inventoryClient.reserveStock(request.getItems());
            
            // Call payment service
            paymentClient.processPayment(request.getAmount());
            
            // Process order
            Order order = processOrder(request);
            
            span.setAttribute("order.status", "success");
            return new OrderResponse(order.getId(), "SUCCESS");
            
        } catch (Exception e) {
            span.recordException(e);
            span.setAttribute("order.status", "failure");
            throw e;
        } finally {
            span.end();
        }
    }
}
```

**Suitable Situations:**

1. For any microservices architecture
2. When debugging distributed failures
3. When identifying performance bottlenecks
4. When understanding service dependencies
5. For monitoring SLAs (latency across services)

**Real-World Use Cases:**

- **Microservices:** Trace requests across services
- **API Gateways:** End-to-end visibility
- **Serverless:** Trace Lambda invocations
- **Message Queues:** Trace async processing
- **Complex Workflows:** Trace business processes

**Advantages**

1. **End-to-End Visibility:** See complete request path
2. **Bottleneck Identification:** Find which service is slow
3. **Failure Localization:** See where errors occur
4. **Dependency Mapping:** Understand service dependencies
5. **SLA Compliance:** Track latency across services

**Disadvantages**

1. **Instrumentation Overhead:** Need to add tracing to all services
2. **Performance Impact:** Tracing adds some overhead
3. **Complexity:** Requires context propagation
4. **Storage Cost:** Traces can be large, sampling needed

**3. Present Solution**
"I would use Pattern X because..."

**4. Discuss Trade-offs**
"This gives us availability but may have eventual consistency. We also need to consider..."

**5. Mention Failure Modes**
"If the service fails, we have circuit breakers. If the database fails, we have..."

**Example: Designing a Highly Available System**

6. **Distributed Cache:** Reduce database load
7. **Read Replicas:** Scale reads

## Chapter 27: Common Interview Questions with Examples

**1. Q: How would you design a system for 1 million concurrent users?**

**A:** I'd design a layered, scalable architecture:

- **CDN:** Serve static content from edge
- **Load Balancer:** Distribute traffic across regions
- **API Gateway:** Single entry point, rate limiting
- **Microservices:** Independently scalable services
- **Distributed Cache:** Redis for frequently accessed data
- **Database:** Read replicas for reads, sharding for writes
- **Queue:** Async processing for non-critical operations
- **Auto-scaling:** Based on CPU/memory metrics

The key is to identify bottlenecks—databases are often first. Use caching to reduce database load, and queue to smooth traffic spikes.

**2. Q: How do you ensure data consistency across microservices?**

**A:** Using the Saga pattern:

For order processing, I'd use orchestration saga:
- **Orchestrator:** Coordinates the saga
- **Commands:** Each step is a command
- **Compensation:** Rollback on failure

Example flow:
1. Create order (pending)
2. Reserve inventory
3. Process payment
4. Confirm order

If payment fails, compensate: release inventory, cancel order.

This gives eventual consistency without distributed transactions.

**3. Q: What's your approach to handling failures in distributed systems?**

**A:** Multiple resilience patterns:

- **Circuit Breaker:** Stop calling failing services
- **Retry with Exponential Backoff:** Handle transient failures
- **Bulkhead:** Isolate failures to components
- **Health Checks:** Detect failures quickly
- **Timeout:** Fail fast, don't wait
- **Fallback:** Degraded responses
- **Supervision:** Restart failed components
- **Redundancy:** Multiple instances

And design for failure: assume services will fail, test failure scenarios, monitor and alert, automate recovery.

**4. Q: How do you scale a distributed system?**

**A:** Multiple strategies:

**Horizontal Scaling:** Add more instances
- Use load balancer
- Stateless services (session in cache)
- Auto-scaling groups

**Data Scaling:**
- **Caching:** Reduce database load
- **Read Replicas:** For read-heavy workloads
- **Sharding:** Partition data across databases
- **CQRS:** Separate read/write paths

**Asynchronous Processing:**
- Queue for decoupling
- Event-driven architecture
- Batch processing

**5. Q: How do you implement zero-downtime deployments?**

**A:** Using Blue-Green or Canary deployment:

**Blue-Green:**
- Maintain two identical environments
- Deploy to Green, test
- Switch traffic instantly
- Rollback by switching back

**Canary:**
- Start with small percentage (1-5%)
- Monitor metrics
- Gradually increase
- Rollback by stopping traffic

Database changes must be backward-compatible for both.

**6. Q: What's the difference between AP and CP systems?**

**A:** According to CAP theorem, during a network partition, you must choose:

**CP Systems (Consistency + Partition Tolerance):**
- All nodes see same data
- May become unavailable during partition
- Examples: ZooKeeper, etcd, HBase
- Use for: banking, inventory

**AP Systems (Availability + Partition Tolerance):**
- Always available
- Data may be temporarily inconsistent
- Examples: Cassandra, DynamoDB
- Use for: social media, shopping carts

The choice depends on your requirements. Banking needs CP; social media can use AP.

**7. Q: How would you debug a distributed system failure?**

**A:** I'd use observability patterns:

- **Distributed Tracing:** See the full request path (Jaeger, Zipkin)
- **Log Aggregation:** Centralize logs (ELK Stack)
- **Metrics Collection:** Monitor key metrics (Prometheus)
- **Correlation IDs:** Track requests across services
- **Health Checks:** Check service status

Steps:
1. Identify affected service from metrics
2. Trace request with trace ID
3. Check logs for errors
4. Review circuit breaker state
5. Check health endpoints
6. Look for patterns (time-based, user-based)

**8. Q: How do you implement rate limiting for a global API?**

**A:** I'd use a distributed rate limiter with Redis:

- **Token Bucket Algorithm:** Allows bursts
- **Redis Lua Scripts:** Atomic operations
- **Per-Client Limits:** Based on API key
- **Headers:** Return limit, remaining, reset

Implementation:
1. Client identified by API key
2. Redis stores token count per client
3. Lua script checks and decrements atomically
4. Reject if no tokens available
5. Return 429 Too Many Requests

For global distribution, use Redis Cluster with replication.

# CONCLUSION

**Key Takeaways**

1. **Design for Failure:** Assume components will fail. Build resilience from day one.

2. **Embrace Trade-offs:** There's no perfect solution. Understand what you're giving up.

3. **Start Simple:** Add complexity only when needed. A well-designed monolith is better than a poorly designed microservices system.

4. **Observability is Essential:** You can't fix what you can't see. Invest in monitoring, logging, and tracing.

5. **Automate Everything:** Manual processes don't scale. Automate deployments, rollbacks, and recovery.

6. **Test Failure Scenarios:** Chaos engineering helps you discover weaknesses before they cause outages.
