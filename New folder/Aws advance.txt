## Chapter 30: Auto Scaling Groups (ASG)

**What is an Auto Scaling Group (ASG)?**

An Auto Scaling Group is a collection of EC2 instances that automatically adjusts capacity based on demand. It ensures you have the right number of instances running at all times.

**Real Scenario**

Your web application experiences traffic spikes during lunch hours and evenings. You don't want to over-provision (wasting money) or under-provision (users experience slowdowns).

**Without ASG:**
- Manual scaling (you add/remove instances yourself)
- Over-provision for peak (expensive)
- Under-provision during spikes (poor performance)

**With ASG:**
- Automatically adds instances when CPU > 70%
- Automatically removes instances when CPU < 30%
- Maintains minimum (2) and maximum (10) instances

**ASG with Load Balancer Integration**

```yaml
# CloudFormation snippet
AutoScalingGroup:
  Type: AWS::AutoScaling::AutoScalingGroup
  Properties:
    VPCZoneIdentifier:
      - subnet-12345
      - subnet-67890
    LaunchTemplate:
      LaunchTemplateId: !Ref WebServerLaunchTemplate
      Version: !GetAtt WebServerLaunchTemplate.LatestVersionNumber
    MinSize: 2
    MaxSize: 10
    DesiredCapacity: 3
    HealthCheckType: ELB
    HealthCheckGracePeriod: 300
    TargetGroupARNs:
      - !Ref WebTargetGroup

ScalingPolicy:
  Type: AWS::AutoScaling::ScalingPolicy
  Properties:
    AutoScalingGroupName: !Ref AutoScalingGroup
    PolicyType: TargetTrackingScaling
    TargetTrackingConfiguration:
      PredefinedMetricSpecification:
        PredefinedMetricType: ASGAverageCPUUtilization
      TargetValue: 70.0
```

**When to Use Auto Scaling Groups**

| Use Case | Why ASG |
|----------|---------|
| **Web applications** | Handle variable traffic |
| **Batch processing** | Scale based on queue size |
| **Microservices** | Scale each service independently |
| **Dev/Test environments** | Schedule scaling to save costs |

**Advantages of ASG**

1. **Automatic scaling:** Responds to demand changes
2. **Cost optimization:** Scale down during low demand
3. **High availability:** Maintain minimum instances across AZs
4. **Self-healing:** Replace failed instances automatically
5. **Integration:** Works with load balancers

**Disadvantages of ASG**

1. **Cold starts:** New instances take minutes to be ready
2. **Configuration complexity:** Many parameters to tune
3. **Scale-in risk:** Removing instances during load spikes
4. **Stateful applications:** Hard to scale (use stateless design)

## Chapter 31: Scaling Policies

**What are Scaling Policies?**

Rules that define when and how an Auto Scaling Group should change its capacity.

**Types of Scaling Policies**

| Policy Type | Description | Use Case |
|-------------|-------------|----------|
| **Target Tracking** | Maintain metric at target value | Simple, set-and-forget |
| **Step Scaling** | Add/remove based on metric thresholds | Gradual response |
| **Simple Scaling** | Single adjustment per alarm | Legacy, not recommended |
| **Scheduled Scaling** | Scale at specific times | Predictable patterns |
| **Predictive Scaling** | ML-based forecasting | Daily/weekly patterns |

## Chapter 32: Health Checks & Self-Healing Systems

**What are Health Checks?**

Mechanisms to determine if an application instance is healthy and able to serve requests.

**Types of Health Checks**

| Type | Level | Description |
|------|-------|-------------|
| **EC2 Status Checks** | Instance | System status (hardware) + Instance status (software) |
| **ELB Health Checks** | Application | HTTP/HTTPS endpoint check |
| **Custom Health Checks** | Application | Custom logic via Lambda |
| **CloudWatch Alarm** | Metric | Based on metric thresholds |

**Health Check Endpoint Implementation**

```python
# Flask health check endpoint
@app.route('/health')
def health_check():
    health_status = {
        'status': 'healthy',
        'checks': {
            'database': check_database(),
            'redis': check_redis(),
            'disk': check_disk_space()
        }
    }
    
    # If any dependency is unhealthy, overall status is unhealthy
    for check, status in health_status['checks'].items():
        if status != 'healthy':
            health_status['status'] = 'unhealthy'
            return jsonify(health_status), 500
    
    return jsonify(health_status), 200

def check_database():
    try:
        db.session.execute('SELECT 1')
        return 'healthy'
    except:
        return 'unhealthy'
```

**Self-Healing Mechanisms**

| Mechanism | Description |
|-----------|-------------|
| **Auto Scaling** | Replaces failed instances automatically |
| **Load Balancer** | Stops sending traffic to unhealthy instances |
| **Route 53** | DNS failover to healthy endpoints |
| **Multi-AZ** | Automatic failover to standby |
| **RDS Multi-AZ** | Automatic database failover |

## Chapter 33: Multi-AZ High Availability Design

**What is Multi-AZ High Availability?**

Deploying resources across multiple Availability Zones (AZs) so that if one AZ fails, the system continues to operate.

**Real Scenario**

Your e-commerce application cannot afford downtime. If a data center loses power, your system must still serve customers.

**Without Multi-AZ:**
- Single AZ: one data center failure = entire application down
- Manual recovery (hours of downtime)

**With Multi-AZ:**
- Resources spread across 2+ AZs
- Automatic failover
- Zero downtime (if designed properly)

**Cross-AZ vs Single-AZ Load Balancer**

| Aspect | Single-AZ ALB | Cross-AZ ALB |
|--------|---------------|--------------|
| **Traffic distribution** | Only to instances in same AZ | To all instances across AZs |
| **AZ failure impact** | 100% loss if that AZ fails | Partial loss (other AZs continue) |
| **Data transfer cost** | Lower (no cross-AZ) | Higher (cross-AZ traffic costs) |
| **Resilience** | Low | High |

**Design Pattern: Active-Active vs Active-Passive**

| Pattern | Description | Failover | Use Case |
|---------|-------------|----------|----------|
| **Active-Active** | All AZs handle traffic | Immediate | Stateless apps |
| **Active-Passive** | One AZ handles traffic, others standby | 60-120 seconds | Stateful apps (databases) |

**Multi-AZ Best Practices**

| Practice | Why |
|----------|-----|
| **Minimum 3 AZs** | If one AZ fails, you still have 2 |
| **Spread instances** | Use ASG across AZs |
| **Use cross-AZ load balancer** | Distribute traffic across AZs |
| **RDS Multi-AZ** | Automatic failover for databases |
| **Test failover** | Regularly test AZ failure scenarios |
| **Monitor across AZs** | Track health per AZ |

## Chapter 34: Terraform Fundamentals

**What is Terraform?**

Terraform is an Infrastructure as Code (IaC) tool that allows you to define and provision infrastructure using a declarative configuration language (HCL - HashiCorp Configuration Language).

**Real Scenario**

Your team needs to create consistent development, staging, and production environments. Manual clicking in AWS console is error-prone and not repeatable.

**Without Terraform:**
- Manual AWS console (slow, error-prone)
- Scripts (boto3, AWS CLI) - imperative, hard to manage
- No state management
- Difficult to track changes

**With Terraform:**

- Version control (Git)

**Terraform Configuration Example (main.tf)**

```hcl
# Provider configuration
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

# Configure AWS provider
provider "aws" {
  region = var.aws_region
}

# Create VPC
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = {
    Name        = "${var.environment}-vpc"
    Environment = var.environment
  }
}

# Create public subnet
resource "aws_subnet" "public" {
  count = length(var.public_subnet_cidrs)

  vpc_id            = aws_vpc.main.id
  cidr_block        = var.public_subnet_cidrs[count.index]
  availability_zone = var.availability_zones[count.index]

  map_public_ip_on_launch = true

  tags = {
    Name        = "${var.environment}-public-subnet-${count.index + 1}"
    Environment = var.environment
  }
}

# Create security group
resource "aws_security_group" "web" {
  name        = "${var.environment}-web-sg"
  description = "Allow HTTP and HTTPS"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
    description = "HTTP from anywhere"
  }

  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
    description = "HTTPS from anywhere"
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "${var.environment}-web-sg"
    Environment = var.environment
  }
}

# Create EC2 instance
resource "aws_instance" "web" {
  count         = var.instance_count
  ami           = var.ami_id
  instance_type = var.instance_type

  subnet_id                   = aws_subnet.public[count.index % length(aws_subnet.public)].id
  vpc_security_group_ids      = [aws_security_group.web.id]
  associate_public_ip_address = true

  user_data = <<-EOF
    #!/bin/bash
    yum update -y
    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
    echo "Hello from instance ${count.index + 1}" > /var/www/html/index.html
  EOF

  tags = {
    Name        = "${var.environment}-web-${count.index + 1}"
    Environment = var.environment
  }
}
```

## Chapter 35: State Management & Remote Backends (S3 + DynamoDB)

**What is Terraform State?**

Terraform state is a file that maps your configuration to real-world resources. It stores resource IDs, attributes, and dependencies.

**Why State Matters**

| Aspect | Importance |
|--------|------------|
| **Resource tracking** | Knows what resources exist |
| **Dependency management** | Understands resource relationships |
| **Performance** | Caches resource attributes |
| **Drift detection** | Identifies manual changes |
| **Collaboration** | Multiple team members need access |

**Problem with Local State**

- **Local file** (terraform.tfstate) stored on your machine
- **Team collaboration** - state conflicts, overwrites
- **CI/CD** - state not accessible
- **Secrets** - may contain sensitive data
- **Accidental deletion** - losing state = losing infrastructure knowledge

**Solution: Remote Backend**

Store state remotely in a shared location with locking.

```
│  │                      (terraform-locks)                                   ││
│  │                                                                           ││
│  │  ┌─────────────────────────────────────────────────────────────────────┐││
│  │  │  LockID          │ Info                                             │││
│  │  ├─────────────────────────────────────────────────────────────────────┤││
│  │  │  dev/terraform   │ {"Operation":"apply","User":"alice","Timestamp":.}│││
│  │  └─────────────────────────────────────────────────────────────────────┘││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                               │
│  Locking Process:                                                             │
│  1. Alice runs `terraform apply`                                            │
│  2. Terraform acquires lock in DynamoDB                                     │
│  3. Bob tries to run `terraform plan`                                       │
│  4. Terraform sees lock → "state locked by Alice" error                     │
│  5. Alice finishes, releases lock                                           │
│  6. Bob can now run commands                                                │
│                                                                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

## Chapter 37: ECR (Elastic Container Registry)

**What is ECR?**

Elastic Container Registry (ECR) is a fully managed Docker container registry that makes it easy to store, manage, and deploy container images.

**Real Scenario**

Your team builds Docker images for multiple microservices. You need a place to store these images and deploy them to ECS or EKS.

**Without ECR:**
- Docker Hub (public images, rate limits)
- Self-hosted registry (additional management)
- No integration with AWS IAM

**With ECR:**
- Fully managed, integrated with AWS
- IAM authentication
- Vulnerability scanning
- Lifecycle policies

**When to Use ECR**

| Use Case | Why ECR |
|----------|---------|
| **Store Docker images** | Managed, secure container registry |
| **CI/CD integration** | Push/pull from build pipelines |
| **ECS/EKS integration** | Native integration with AWS compute |
| **Vulnerability scanning** | Built-in image scanning |
| **Lifecycle management** | Automatic image cleanup |

**Advantages of ECR**

1. **Fully managed:** No servers to maintain
2. **Integrated with IAM:** Fine-grained access control
3. **High availability:** 99.9% availability SLA
4. **Vulnerability scanning:** Basic scanning included
5. **Lifecycle policies:** Automatic image cleanup
6. **Cross-region replication:** Copy images across regions

**Disadvantages of ECR**

1. **AWS only:** Not multi-cloud (though can be used with other clouds)
2. **Cost:** Storage and data transfer costs
3. **Learning curve:** Different from Docker Hub

**ECR vs Docker Hub**

| Aspect | ECR | Docker Hub |
|--------|-----|------------|
| **Integration** | AWS native | Universal |
| **Authentication** | IAM | Docker ID |
| **Private repos** | Unlimited (pay for storage) | 1 free private |
| **Vulnerability scanning** | Basic included | Enhanced with paid plan |
| **Rate limits** | Based on AWS account | Pull rate limits |
| **Best for** | AWS workloads | Open source, public images |

## Chapter 38: Image Management & Versioning

**What is Image Management?**

The practice of organizing, tagging, storing, and maintaining container images throughout their lifecycle.

**Image Tagging Strategies**

| Strategy | Example | Pros | Cons |
|----------|---------|------|------|
| **Latest** | `myapp:latest` | Simple | No version history |
| **Semantic version** | `myapp:v1.2.3` | Clear versioning | Manual updates |
| **Git commit hash** | `myapp:abc123` | Traceable | Hard to compare |
| **Build number** | `myapp:build-123` | Unique, sequential | Not semantic |
| **Date-based** | `myapp:2024-01-15` | Temporal | Long names |

**Best Practice: Multiple Tags**

```bash
# Tag with multiple identifiers
docker tag myapp:local 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:latest
docker tag myapp:local 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:v1.2.3
docker tag myapp:local 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:abc123

# Push all tags
docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp --all-tags
```

**Image Versioning Strategy**

```yaml
          image-ref: myapp:latest
          format: 'sarif'
          output: 'trivy-results.sarif'
          severity: 'CRITICAL,HIGH'
      
      - name: Fail if critical vulnerabilities found
        run: |
          if grep -q '"severity":"CRITICAL"' trivy-results.sarif; then
            echo "Critical vulnerabilities found!"
            exit 1
          fi
```

**Image Scanning Best Practices**

| Practice | Why |
|----------|-----|
| **Scan on every push** | Catch vulnerabilities early |
| **Block critical/high** | Prevent vulnerable images |
| **Use minimal base images** | Fewer vulnerabilities |
| **Regular base image updates** | Patch known CVEs |
| **Pin base image versions** | Reproducible builds |
| **Monitor vulnerability databases** | New CVEs discovered daily |
| **Automated remediation** | Rebuild images automatically |

## Chapter 40: Blue-Green Deployment

**What is Blue-Green Deployment?**

A deployment strategy that uses two identical environments (blue and green). Only one environment serves live traffic at a time, enabling instant rollbacks.

**Real Scenario**

You need to deploy a new version of your application with zero downtime and instant rollback capability.

**Without Blue-Green:**
- Rolling deployment (some users see old version, some new)
- Slow rollback (requires redeployment)
- Risk of downtime

**With Blue-Green:**
- Zero downtime (instant switch)
- Instant rollback (switch back)
- Full testing in production environment

**Advantages of Blue-Green**

1. **Zero downtime:** Instant switch
2. **Instant rollback:** Switch back to previous version
3. **Full testing:** Test in production environment

**Disadvantages of Blue-Green**

1. **Double infrastructure:** Two complete environments
2. **Database challenges:** Schema must be compatible
3. **Stateful services:** Harder to handle state
4. **Cost:** Double the resources during deployment

## Chapter 41: Rolling Deployment

**What is Rolling Deployment?**

Gradually replaces instances of the old version with new version, one batch at a time, while keeping the application available.

**Real Scenario**

You need to deploy a new version with zero downtime, but you don't want to double your infrastructure costs.

**Without Rolling:**
- Blue-green requires double infrastructure
- In-place deployment causes downtime

**With Rolling:**
- Gradual replacement (batch size: 1-2 instances)
- Zero downtime (if configured correctly)
- No additional infrastructure cost

|----------|-------------|

**Advantages of Rolling Deployment**

1. **Mixed versions during deployment:** May cause issues
2. **Slow rollback:** Must roll back batches

4. **Stateful challenges:** State must be compatible

| **Rollback speed** | Slow (per batch) | Instant (switch traffic) |
| **Testing before release** | Limited | Full testing |
| **Mixed versions** | Yes | No |

## Chapter 42: Canary Releases

**What is Canary Release?**

Gradually roll out a new version to a small subset of users first, monitor for issues, then gradually increase the percentage.

**Real Scenario**

You want to test a new feature with real production traffic before rolling out to all users.

**Without Canary:**
- Blue-green: all users at once
- Rolling: all users eventually get new version
- No gradual testing with real traffic

**With Canary:**
- Start with 1% of users
- Monitor metrics (errors, latency)
- Increase to 10%, 25%, 50%, 100%
- Rollback instantly if issues detected

```bash
#!/bin/bash

# Initial canary (1%)
update_weight() {
  local v1_weight=$1
  local v2_weight=$2
  
  aws elbv2 modify-listener --listener-arn $LISTENER_ARN \
    --default-actions "[
      {\"Type\":\"forward\",\"ForwardConfig\":{
        \"TargetGroups\":[
          {\"TargetGroupArn\":\"$V1_TG_ARN\",\"Weight\":$v1_weight},
          {\"TargetGroupArn\":\"$V2_TG_ARN\",\"Weight\":$v2_weight}
        ]
      }}
    ]"
}

# Deploy v2 to canary target group
aws ecs update-service --cluster my-cluster --service v2-service --force-new-deployment
wait_for_service_stable "v2-service"

# Start canary with 1%
update_weight 99 1

# Monitor for 5 minutes
sleep 300

# Check metrics (error rate, latency)
ERROR_RATE=$(get_error_rate)
if [ $ERROR_RATE -gt 1 ]; then
  echo "Error rate too high, rolling back"
  update_weight 100 0
  exit 1
fi

# Increase to 10%
update_weight 90 10
sleep 300

# Increase to 50%
update_weight 50 50
sleep 300

# Full rollout
update_weight 0 100
```

## Chapter 43: Rollback Strategies

**What are Rollback Strategies?**

Plans and mechanisms to quickly revert to a known good state when a deployment causes issues.

**Real Scenario**

You deployed version 2.0, but immediately see error rates spiking. You need to revert to version 1.0 as fast as possible.

**Without Rollback Strategy:**
- Manual re-deployment (slow, error-prone)
- Extended outage
- Customer impact

**With Rollback Strategy:**
- Instant or automated rollback
- Minimal customer impact
- Fast recovery

**Diagram: Rollback Strategies**

```

│                         ROLLBACK STRATEGIES                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                               │
│  TYPE 1: BLUE-GREEN ROLLBACK                                                 │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
```

## Chapter 44: CloudWatch Logs vs Metrics

**What's the Difference?**

| Aspect | Metrics | Logs |
|--------|---------|------|
| **Data type** | Numerical (time-series) | Text (unstructured/semi-structured) |
| **Purpose** | Performance, capacity | Debugging, audit, troubleshooting |
| **Query** | Statistical (avg, sum, max) | Text search, pattern matching |
| **Storage cost** | Lower | Higher |
| **Retention** | 15 months default | Configurable (1 day to 10 years) |
| **Alerts** | Yes (metric alarms) | Yes (metric filters → alarm) |

**Metric Filters (Logs → Metrics)**

Extract metrics from log data.

```bash
# Create metric filter for error count
aws logs put-metric-filter \
  --log-group-name /aws/lambda/my-function \
  --filter-name ErrorCount \
  --filter-pattern "ERROR" \
  --metric-transformations \
    metricName=ErrorCount,metricNamespace=MyApp,metricValue=1

# Create alarm from metric filter
aws cloudwatch put-metric-alarm \
  --alarm-name HighErrorRate \
  --alarm-description "Error rate > 1%" \
  --metric-name ErrorCount \
  --namespace MyApp \
  --statistic Sum \
  --period 60 \
  --evaluation-periods 5 \
  --threshold 10 \
  --comparison-operator GreaterThanThreshold
```

```javascript
const AWSXRay = require('aws-xray-sdk-core');
const AWS = AWSXRay.captureAWS(require('aws-sdk'));
const express = require('express');
const app = express();

// Capture all incoming requests
app.use(AWSXRay.express.openSegment('my-app'));

app.get('/api/orders/:id', async (req, res) => {
  // Subsegment for database query
  const subsegment = AWSXRay.getSegment().addNewSubsegment('DatabaseQuery');
  try {

    res.json(result);

    res.status(500).json({ error: err.message });
  }
});
```

**Custom Config Rule (Lambda)**

```javascript
exports.handler = async (event, context) => {
  const evaluatingControls = event.configRuleInvokingEvent;
  const invokingEvent = JSON.parse(event.invokingEvent);
  const configurationItem = invokingEvent.configurationItem;
  
  // Check if resource is compliant
  let complianceType = 'COMPLIANT';
  
  if (configurationItem.resourceType === 'AWS::EC2::Instance') {
    const instanceType = configurationItem.configuration.instanceType;
    
    // Only allow approved instance types
    const approvedTypes = ['t3.micro', 't3.small', 'm5.large'];
    
    if (!approvedTypes.includes(instanceType)) {
      complianceType = 'NON_COMPLIANT';
    }
  }
  
  // Return evaluation result
  await putEvaluations({
    EvaluationType: 'CUSTOM_POLICY',
    ResultToken: event.resultToken,
    Evaluations: [{
      ComplianceResourceType: configurationItem.resourceType,
      ComplianceResourceId: configurationItem.resourceId,
      ComplianceType: complianceType,
      OrderingTimestamp: configurationItem.configurationItemCaptureTime
    }]
  });
};
```

## Chapter 52: IAM Policy Evaluation Logic

**How IAM Evaluates Policies**

IAM policies are evaluated in a specific order to determine whether to allow or deny access.

**Diagram: IAM Policy Evaluation Flow**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    IAM POLICY EVALUATION FLOW                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                               │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
│  │                         START                                            ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                    │                                         │
│                                    ▼                                         │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
│  │                    Is there an explicit DENY?                            ││
│  │                                                                           ││
│  │  Check:                                                                  ││
│  │  • Identity-based policies (user, group, role)                          ││
│  │  • Resource-based policies (bucket policy, queue policy)                ││
│  │  • Permission boundaries                                                ││
│  │  • Session policies (for role sessions)                                 ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                    │                                         │
│                    ┌───────────────┴───────────────┐                        │
│                    │ Yes                           │ No                     │
│                    ▼                               ▼                        │
│              ┌──────────┐              ┌─────────────────────────────────┐ │
│              │  DENY    │              │  Is there an explicit ALLOW?     │ │
│              │  Access  │              │                                   │ │
│              │  Denied  │              │  Check:                           │ │
│              └──────────┘              │  • Identity-based policies        │ │
│                                        │  • Resource-based policies       │ │
│                                        │  • Service control policies (SCP)│ │
│                                        └─────────────────────────────────┘ │
│                                                    │                         │
│                                    ┌───────────────┴───────────────┐        │
│                                    │ Yes                           │ No     │
│                                    ▼                               ▼        │
│                              ┌──────────┐                   ┌──────────┐   │
│                              │  ALLOW   │                   │  DENY    │   │
│                              │  Access  │                   │ Default  │   │
│                              │  Granted │                   │  Deny    │   │
│                              └──────────┘                   └──────────┘   │
│                                                                               │
│  Key Rules:                                                                   │
│  • Explicit DENY overrides any ALLOW                                         │
│  • Default is DENY (implicit)                                               │
│  • First DENY encountered stops evaluation                                   │
│                                                                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Policy Evaluation Example**

```json
{
  "Effect": "DENY",
  "Action": "s3:DeleteBucket",
  "Resource": "*"
}
```
vs
```json
{
  "Effect": "ALLOW",
  "Action": "s3:*",
  "Resource": "*"
}
```

**Result:** DENY wins (explicit deny overrides allow)

**Multiple Policies (Union of Permissions)**

When multiple policies apply, permissions are combined (union). If any policy allows an action and no policy denies it, the action is allowed.

**Condition Keys (Contextual Evaluation)**

```json
{
  "Effect": "Allow",

    "Bool": {

    }
  }
}
```

## Chapter 53: Least Privilege Design

**What is Least Privilege?**

The principle of granting only the minimum permissions necessary to perform a task.

**Real Scenario**

Your application needs to read from an S3 bucket. It doesn't need to write or delete.

**Without Least Privilege:**
- Grant `s3:*` (all S3 permissions)
- Security risk (could delete data)
- Compliance violation

**With Least Privilege:**
- Grant only `s3:GetObject`
- Scoped to specific bucket and prefix
- Reduced risk

**Diagram: Least Privilege vs Overly Permissive**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    LEAST PRIVILEGE vs OVERLY PERMISSIVE                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                               │
│  OVERLY PERMISSIVE (❌ Bad)                                                   │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
│  │  {                                                                        ││
│  │    "Effect": "Allow",                                                     ││
│  │    "Action": "*",          ← All actions                                 ││
│  │    "Resource": "*"         ← All resources                               ││
│  │  }                                                                        ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                               │
│  LEAST PRIVILEGE (✅ Good)                                                    │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
│  │  {                                                                        ││
│  │    "Effect": "Allow",                                                     ││
│  │    "Action": [                                                            ││
│  │      "s3:GetObject",      ← Only needed action                          ││
│  │      "s3:ListBucket"                                                      ││
│  │    ],                                                                     ││
│  │    "Resource": [                                                          ││
│  │      "arn:aws:s3:::my-bucket",          ← Specific bucket               ││
│  │      "arn:aws:s3:::my-bucket/*"         ← Specific path                 ││
│  │    ]                                                                      ││
│  │  }                                                                        ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Least Privilege Steps**

| Step | Action |
|------|--------|
| 1 | Identify the task (e.g., "read from S3") |
| 2 | Determine required actions (e.g., `s3:GetObject`) |
| 3 | Scope to specific resources (e.g., `my-bucket/logs/*`) |
| 4 | Add conditions if needed (e.g., IP restriction) |
| 5 | Test with least privilege |
| 6 | Monitor and refine |

**Tools for Least Privilege**

| Tool | Purpose |
|------|---------|
| **IAM Access Analyzer** | Generate least privilege policies |
| **IAM Policy Simulator** | Test policies before applying |
| **CloudTrail** | See what actions are actually used |
| **IAM Access Advisor** | Show last accessed information |

**IAM Access Analyzer (Generate Least Privilege Policy)**

```bash
# Generate policy based on CloudTrail logs
aws accessanalyzer generate-finding \
  --analyzer-arn arn:aws:access-analyzer:us-east-1:123456789012:analyzer/my-analyzer

# Generate policy from activity
aws accessanalyzer generate-policy \
  --principal-arn arn:aws:iam::123456789012:role/my-role \
  --days 30
```

**Least Privilege Best Practices**

| Practice | Why |
|----------|-----|
| **Start with no permissions** | Add only what's needed |
| **Use managed policies when possible** | AWS-managed, regularly updated |
| **Scope resources** | Don't use `Resource: "*"` |
| **Use conditions** | IP, MFA, tags |
| **Review regularly** | Remove unused permissions |
| **Use IAM Access Analyzer** | Generate least privilege policies |
| **Test with policy simulator** | Validate before applying |

## Chapter 54: IAM Roles vs Users (Best Practices)

**What's the Difference?**

| Aspect | IAM User | IAM Role |
|--------|----------|----------|
| **Purpose** | Individual human | Service or temporary access |
| **Credentials** | Long-term (password + access keys) | Temporary (session-based) |
| **Rotation** | Manual | Automatic (AWS STS) |
| **Shared access** | Not recommended | Yes (assumed by multiple) |
| **Use case** | Human users | EC2, Lambda, cross-account |

**Best Practices**

| Practice | Why |
|----------|-----|
| **No root user access** | Root has full permissions, use only for account setup |
| **Use roles for services** | Never store credentials on EC2 |
| **Use roles for cross-account** | Trust relationships instead of access keys |
| **Use groups for users** | Manage permissions by role |
| **Enable MFA** | Adds security layer |
| **Rotate access keys** | Every 90 days |
| **Delete unused keys** | Reduce attack surface |

**Role vs User Example**

```yaml
# ❌ Bad: Store credentials on EC2
ENV:
  AWS_ACCESS_KEY_ID: AKIAIOSFODNN7EXAMPLE
  AWS_SECRET_ACCESS_KEY: wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY

# ✅ Good: EC2 assumes role
ec2_role:
  Type: AWS::IAM::Role
  Properties:
    AssumeRolePolicyDocument:
      Statement:
        - Effect: Allow
          Principal:
            Service: ec2.amazonaws.com
          Action: sts:AssumeRole
    ManagedPolicyArns:
      - arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess
```

## Chapter 55: Cross-Account Access

**What is Cross-Account Access?**

Allowing principals (users or roles) in one AWS account to access resources in another AWS account.

**Real Scenario**

Your organization has separate AWS accounts for development, staging, and production. Developers need access to all accounts.

**Without Cross-Account Access:**
- Separate credentials for each account
- Manual role switching
- Security risk (multiple sets of keys)

**With Cross-Account Access:**
- Assume role from dev account to prod
- Single set of credentials
- Audit trail via CloudTrail

## Chapter 57: Envelope Encryption

**What is Envelope Encryption?**

Using a master key (KEK) to encrypt data keys (DEK), which then encrypt data. This allows efficient key rotation and reduces KMS costs.

**Real Scenario**

You need to encrypt thousands of files in S3. Using KMS directly for each file would be expensive (KMS API calls cost money).

**Without Envelope Encryption:**
- Call KMS for every file (costly)
- KMS has rate limits
- Each file = one API call

**With Envelope Encryption:**
- Generate one data key per file
- Encrypt file with data key (local, fast)
- Encrypt data key with KMS (only once per file)
- Pay only for KMS API calls (one per file)

**Diagram: Envelope Encryption**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         ENVELOPE ENCRYPTION                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                               │
│  STEP 1: Generate Data Key (DEK)                                            │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
│  │                                                                           ││
│  │  AWS KMS (Master Key / KEK)                                             ││
│  │         │                                                                ││
│  │         │ GenerateDataKey                                               ││
│  │         ▼                                                                ││
│  │  ┌─────────────────┐     ┌─────────────────┐                           ││
│  │  │ Data Key (DEK)  │     │ Encrypted DEK   │                           ││
│  │  │ (Plaintext)     │     │ (Ciphertext)    │                           ││
│  │  └─────────────────┘     └─────────────────┘                           ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                               │
│  STEP 2: Encrypt Data                                                        │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
│  │                                                                           ││
│  │  ┌─────────────┐     ┌─────────────┐     ┌─────────────┐               ││
│  │  │   Data      │────▶│ Encrypted   │     │ Encrypted   │               ││
│  │  │ (File)      │     │   Data      │     │    DEK      │               ││
│  │  └─────────────┘     └─────────────┘     └─────────────┘               ││
│  │         │                   │                   │                        ││
│  │         │                   └───────────────────┼───────────────────────┐││
│  │         │                                       │                       │││
│  │         └───────────────────────────────────────┼───────────────────────┘││
│  │                                                 │                         ││
│  │                                                 ▼                         ││
│  │                                     ┌─────────────────────┐             ││
│  │                                     │ Encrypted File      │             ││
│  │                                     │ + Encrypted DEK     │             ││
│  │                                     └─────────────────────┘             ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                               │
│  Benefits:                                                                   │
│  • Data keys can be cached (reuse for multiple files)                       │
│  • Only DEK needs KMS (not entire file)                                     │
│  • Master key rotation is simple (re-encrypt DEKs)                          │
│                                                                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

**S3 Server-Side Encryption with KMS (SSE-KMS) - Uses envelope encryption**

```hcl
resource "aws_s3_bucket" "encrypted_bucket" {
  bucket = "my-encrypted-bucket"
}

resource "aws_s3_bucket_server_side_encryption_configuration" "example" {
  bucket = aws_s3_bucket.encrypted_bucket.id

  rule {
    apply_server_side_encryption_by_default {
      kms_master_key_id = aws_kms_key.mykey.arn
      sse_algorithm     = "aws:kms"
    }
  }
}
```

**Custom Envelope Encryption (AWS Encryption SDK)**

```javascript
const AWS = require('aws-sdk');
const { KmsKeyringNode } = require('@aws-crypto/client-node');
const { encrypt, decrypt } = require('@aws-crypto/client-node');

const kms = new AWS.KMS({ region: 'us-east-1' });

async function encryptFile(data, keyArn) {
  // Create keyring with KMS master key
  const keyring = new KmsKeyringNode({ generatorKeyId: keyArn });
  
  // Encrypt data (envelope encryption automatically)
  const { result } = await encrypt(keyring, data);
  
  // result contains encrypted data + encrypted data keys
  return result;
}

async function decryptFile(encryptedData, keyArn) {
  const keyring = new KmsKeyringNode({ generatorKeyId: keyArn });
  const { plaintext } = await decrypt(keyring, encryptedData);
  return plaintext;
}
```

## Chapter 58: Key Rotation Strategies

**What is Key Rotation?**

Replacing old encryption keys with new ones to limit exposure if a key is compromised.

**Key Rotation Strategies**

| Strategy | Description | Use Case |
|----------|-------------|----------|
| **Automatic (AWS-managed)** | AWS rotates keys automatically | Default, low effort |
| **Manual (Customer-managed)** | You rotate keys manually | Compliance, custom schedule |
| **Alias-based** | Update alias to point to new key | Zero-downtime rotation |
| **Re-encrypt** | Re-encrypt data with new key | Strong security |

**KMS Key Rotation**

```hcl
resource "aws_kms_key" "rotating_key" {
  description             = "Key with automatic rotation"
  enable_key_rotation     = true  # Automatic rotation every year
  deletion_window_in_days = 7
}

# Custom rotation schedule (Lambda)
resource "aws_lambda_function" "rotate_key" {
  filename         = "rotate.zip"
  function_name    = "rotate-kms-key"
  role             = aws_iam_role.rotation_role.arn
  handler          = "index.handler"
  runtime          = "nodejs18.x"
}

# Schedule rotation monthly
resource "aws_cloudwatch_event_rule" "key_rotation" {
  name                = "key-rotation-schedule"
  schedule_expression = "cron(0 0 1 * ? *)"  # 1st of every month
}

resource "aws_cloudwatch_event_target" "rotate" {
  rule = aws_cloudwatch_event_rule.key_rotation.name
  arn  = aws_lambda_function.rotate_key.arn
}
```

**Data Key Rotation (Re-encryption)**

```javascript
async function rotateDataKeys(bucket, prefix, newKeyArn) {
  const s3 = new AWS.S3();
  const kms = new AWS.KMS();
  
  // List all objects
  const objects = await s3.listObjectsV2({ Bucket: bucket, Prefix: prefix }).promise();
  
  for (const object of objects.Contents) {
    // Download encrypted object
    const data = await s3.getObject({ Bucket: bucket, Key: object.Key }).promise();
    
    // Decrypt with old key (KMS tracks which key was used)
    const decrypted = await kms.decrypt({ CiphertextBlob: data.Body }).promise();
    
    // Re-encrypt with new key
    const reencrypted = await kms.encrypt({
      KeyId: newKeyArn,
      Plaintext: decrypted.Plaintext
    }).promise();
    
    // Upload re-encrypted object
    await s3.putObject({
      Bucket: bucket,
      Key: object.Key,
      Body: reencrypted.CiphertextBlob
    }).promise();
  }
}
```

**Key Rotation Best Practices**

| Practice | Why |
|----------|-----|
| **Enable automatic rotation** | AWS-managed, no effort |
| **Rotate data keys regularly** | Limit exposure window |
| **Use aliases for customer-managed** | Abstract key IDs |
| **Monitor key usage** | Detect unusual patterns |
| **Test rotation process** | Ensure it works |

## Chapter 60: Secrets Handling in Pipelines

**What is Secrets Handling?**

Securely managing and accessing secrets (API keys, passwords, tokens) in CI/CD pipelines.

**GitHub Actions Secrets Example**

```yaml
# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v1
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: us-east-1
      
      - name: Retrieve database password
        run: |
          DB_PASSWORD=$(aws secretsmanager get-secret-value \
            --secret-id prod/db/password \
            --query SecretString \
            --output text)
          
          # Use password (without logging)
          echo "::add-mask::$DB_PASSWORD"
          ./deploy.sh --db-password "$DB_PASSWORD"
```

| Practice | Why |
|----------|-----|

| **Use secrets manager** | Centralized, audited |
| **Mask secrets in logs** | Prevent accidental exposure |
| **Rotate regularly** | Limit exposure window |
| **Least privilege** | Pipeline only needs deploy permissions |
| **Audit secret access** | Detect unauthorized access |
| **Use OIDC instead of long-term keys** | Temporary credentials |

## Chapter 64: IAM Roles for Service Accounts (IRSA)

**What is IRSA?**

Allows Kubernetes pods to assume IAM roles directly, without storing credentials in the pod.

**Real Scenario**

Your pod needs to access S3. You don't want to store AWS credentials in environment variables or as secrets.

**Without IRSA:**
- Store AWS credentials in pod (security risk)
- Long-lived access keys
- Hard to rotate

**With IRSA:**
- Pod assumes IAM role
- Temporary credentials via OIDC
- No credentials stored in pod

**Diagram: IRSA Flow**

```

│  │  │  Service Account: my-app-sa                                         │││
│  │  │  annotations:                                                        │││
│  │  │    eks.amazonaws.com/role-arn: arn:aws:iam::123456:role/s3-access  │││
```

**IRSA Configuration**

```hcl
# 1. Create IAM role for service account
resource "aws_iam_role" "s3_access" {
  name = "s3-access-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          Federated = aws_iam_openid_connect_provider.eks.arn
        }
        Action = "sts:AssumeRoleWithWebIdentity"
        Condition = {
          StringEquals = {
            "${aws_iam_openid_connect_provider.eks.url}:aud" = "sts.amazonaws.com"
            "${aws_iam_openid_connect_provider.eks.url}:sub" = "system:serviceaccount:default:my-app-sa"
          }
        }
      }
    ]
  })
}

resource "aws_iam_role_policy_attachment" "s3_access" {
  role       = aws_iam_role.s3_access.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess"
}

# 2. Create Kubernetes service account
resource "kubernetes_service_account" "my_app" {
  metadata {
    name = "my-app-sa"
    annotations = {
      "eks.amazonaws.com/role-arn" = aws_iam_role.s3_access.arn
    }
  }
}
```

Kubernetes resource that manages external access to services, typically HTTP/HTTPS traffic.

**Real Scenario**

You have multiple services (api, web, admin) and need to route traffic to them based on URL path (api/*, admin/*, /*).

**Without Ingress:**
- Each service needs its own load balancer (expensive)
- Manual routing configuration
- No SSL termination at cluster level

**With Ingress:**
- One load balancer for multiple services
- Path-based routing
- SSL termination at Ingress

## Chapter 67: Public vs Private Subnets (Deep Dive)

**What are Subnets?**

Subnets are subdivisions of a VPC's IP address range. They group resources and control network access.

**Public Subnet**
- Has direct route to Internet Gateway
- Resources get public IPs (optional)
- Can receive inbound traffic from internet
- Use for: Load balancers, web servers, NAT gateways

**Private Subnet**
- No direct route to Internet Gateway
- Resources have private IPs only
- Cannot receive inbound traffic from internet
- Use for: Application servers, databases

## Chapter 68: NAT Gateway

**What is NAT Gateway?**

Network Address Translation (NAT) Gateway allows instances in private subnets to access the internet (for updates, patches, external APIs) while preventing inbound traffic from the internet.

**Real Scenario**

Your application servers in private subnets need to download security patches and call external APIs, but should not receive inbound internet traffic.

**Without NAT Gateway:**
- Private subnets can't reach internet
- Can't download updates
- Can't call external APIs

**With NAT Gateway:**
- Private instances can initiate outbound connections
- Inbound connections blocked
- Single public IP for all private instances

**Diagram: NAT Gateway Flow**

## Chapter 69: Internet Gateway

**What is Internet Gateway?**

Horizontally scaled, redundant, and highly available VPC component that allows communication between your VPC and the internet.

**Real Scenario**

Your web servers need to serve traffic to users on the internet.

**Without Internet Gateway:**
- No inbound internet access
- Resources can't be reached from internet

**With Internet Gateway:**
- Public subnets can receive inbound internet traffic
- Resources can have public IPs
- Required for public-facing applications

## Chapter 71: Spot Instances

**What are Spot Instances?**

EC2 instances that use unused capacity at up to 90% discount, but can be reclaimed with 2-minute notice.

**Real Scenario**

You have batch processing jobs that can be interrupted. You want to save costs.

**Without Spot:**
- On-Demand instances: $0.10/hour
- 1000 instances × 100 hours = $10,000

**With Spot:**
- Spot instances: $0.01/hour (90% savings)
- 1000 instances × 100 hours = $1,000

**Diagram: Spot Instance Lifecycle**

## Chapter 74: SQS (Simple Queue Service)

**What is SQS?**

Fully managed message queuing service for decoupling application components.

**Real Scenario**

Your order processing system receives 1000 orders per second. You need to process them without overwhelming the backend.

**Without SQS:**
- Direct calls to backend (synchronous)
- Backend gets overwhelmed
- Orders dropped

**With SQS:**
- Orders go to queue
- Workers pull at their own pace
- No orders dropped

```
│  │  │ API      │  │ Lambda   │  │ EC2      │                              ││
│  │  │ Gateway  │  │          │  │          │                              ││
```

**SQS Terraform**

```hcl
# Standard queue (high throughput)
resource "aws_sqs_queue" "standard_queue" {
  name                      = "order-queue"
  delay_seconds             = 0
  max_message_size          = 262144
  message_retention_seconds = 86400
  receive_wait_time_seconds = 20
  visibility_timeout_seconds = 30

  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.dead_letter_queue.arn
    maxReceiveCount     = 3
  })

  tags = {
    Environment = "production"
  }
}

# FIFO queue (strict ordering)

  visibility_timeout_seconds  = 30

  tags = {
    Environment = "production"
  }
}

# Dead letter queue
resource "aws_sqs_queue" "dead_letter_queue" {
  name = "order-queue-dlq"
  message_retention_seconds = 1209600  # 14 days
}
```

## Chapter 75: SNS (Pub/Sub)

**What is SNS?**

Fully managed publish/subscribe messaging service for broadcasting messages to multiple subscribers.

**Real Scenario**

When a new user registers, you need to send welcome email, update analytics, notify CRM, and trigger onboarding.

**Without SNS:**
- User service calls each service directly (tight coupling)
- Adding new subscriber requires code change
- Subscriber failures affect user service

**With SNS:**
- User service publishes one message to topic
- All subscribers receive message independently
- Add new subscribers without code change

**Diagram: SNS Architecture**


# CONCLUSION

**Key Takeaways from All Additional Chapters**

**Compute Scaling**
- Auto Scaling Groups provide automatic capacity adjustment
- Target tracking is simplest scaling policy
- Health checks enable self-healing systems
- Multi-AZ design is essential for high availability

**Infrastructure as Code**
- Terraform enables declarative infrastructure
- Remote state (S3 + DynamoDB) enables team collaboration
- Modules enable reusable infrastructure components

**Container Ecosystem**
- ECR provides managed container registry
- Tag images with semantic version and commit hash
- Scan images for vulnerabilities before deployment

**Deployment Strategies**
- Blue-green for zero downtime and instant rollback
- Canary for risk reduction with real traffic
- Rolling for cost-sensitive workloads

**Observability**
- Metrics for performance, logs for debugging
- Alarms should be actionable
- X-Ray for distributed tracing

**Auditing & Security**
- CloudTrail for API auditing (who did what)
- AWS Config for compliance and drift detection
- GuardDuty for threat detection
- Security Hub for centralized view

**IAM & Security**
- Least privilege principle
- Use roles, not users, for services
- Cross-account access via role assumption

**Encryption**
- At rest (EBS, S3) and in transit (TLS)
- Envelope encryption reduces KMS calls
- Rotate keys regularly

**CI/CD Security**
- Scan code, dependencies, containers
- Never store secrets in code
- Environment approvals for production

**Kubernetes (EKS)**
- Node groups for different workloads
- IRSA for pod IAM permissions
- Ingress for external HTTP traffic
- Network policies for zero trust

**Networking**
- Public subnets for internet-facing resources
- Private subnets for internal resources
- NAT Gateway for private subnet internet access
- VPC endpoints for private AWS service access

**Cost Optimization**
- Spot instances for fault-tolerant workloads
- Reserved instances for steady-state
- Right-size resources based on metrics

**Event-Driven**
- SQS for work queues
- SNS for pub/sub
- EventBridge for complex event routing

**Multi-Account & DR**
- Separate accounts for environments
- Centralized logging and security
- Define RTO/RPO based on business needs
