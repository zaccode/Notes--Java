## Chapter 1: What is Cloud Computing

**Simple Definition**

Cloud computing is the delivery of computing services—servers, storage, databases, networking, software—over the internet ("the cloud") instead of owning and maintaining physical data centers and servers.

**Technical Definition**

Cloud computing is a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources that can be rapidly provisioned and released with minimal management effort or service provider interaction.

**Evolution: On-Premise → Virtualization → Cloud**

| Era | Approach | Description | Pros | Cons |
|-----|----------|-------------|------|------|
| **1990s-2000s** | On-Premise | Own servers in your data center | Full control | Expensive, hard to scale |
| **2000s-2010s** | Virtualization | VMs on shared hardware | Better utilization | Still need hardware |
| **2010s+** | Cloud | Rent resources on demand | Pay as you go, elastic | Less control |

**Real-World Analogy: Renting vs Owning a Home**

- **On-Premise (Owning):** You buy land, build a house, maintain everything. You have full control but high upfront cost and ongoing maintenance.

- **Cloud (Renting):** You rent an apartment. You pay only for what you use. Someone else handles maintenance, security, utilities. You can move out anytime.

**Why Cloud Exists**

1. **Cost Efficiency:** Pay only for what you use (no upfront hardware costs)
2. **Elasticity:** Scale up during demand, scale down during low usage
3. **Global Reach:** Deploy applications close to users worldwide
4. **Reliability:** Built-in redundancy, backups, disaster recovery
5. **Speed:** Deploy resources in minutes, not weeks
6. **Focus:** Developers focus on code, not infrastructure

**Key Characteristics of Cloud (NIST Definition)**

1. **On-Demand Self-Service:** Provision resources without human interaction
2. **Broad Network Access:** Accessible from anywhere (internet)
3. **Resource Pooling:** Multi-tenant model, resources shared
4. **Rapid Elasticity:** Scale out/in quickly
5. **Measured Service:** Pay-per-use metering

## Chapter 2: Types of Cloud

**1. Public Cloud**

Cloud services offered over the public internet, shared across multiple organizations.

**Examples:** AWS, Microsoft Azure, Google Cloud Platform (GCP)

**Characteristics:**
- Services delivered over public internet
- Shared infrastructure (multi-tenant)
- Pay-as-you-go pricing
- No hardware to manage

**IaaS (Infrastructure as a Service)**

**Definition:** Provides virtualized computing resources over the internet. You rent servers, storage, networking.

**What you manage:** Applications, data, runtime, middleware, OS
**Provider manages:** Virtualization, servers, storage, networking

**When to use:**
- Need full control over OS and software
- Running custom applications
- Lift-and-shift migration
- Need specific configurations

**Examples:** AWS EC2, Google Compute Engine, Azure Virtual Machines

**Real scenario:** Hosting a web application with specific security requirements

---

**PaaS (Platform as a Service)**

**Definition:** Provides a platform to develop, run, and manage applications without managing infrastructure.

**What you manage:** Applications, data
**Provider manages:** Runtime, middleware, OS, virtualization, servers, storage, networking

**When to use:**
- Want to focus on coding, not infrastructure
- Rapid development and deployment
- Don't need OS-level control
- Building web applications

**Examples:** Heroku, Google App Engine, AWS Elastic Beanstalk

**Real scenario:** A startup building a web app wants to deploy quickly without managing servers

---

**SaaS (Software as a Service)**

**Definition:** Provides ready-to-use software over the internet.

**What you manage:** Nothing (just use the application)
**Provider manages:** Everything

**When to use:**
- Need standard business applications
- No customization needed
- Want zero maintenance
- Pay per user

**Examples:** Gmail, Salesforce, Dropbox, Office 365, Slack

**Real scenario:** A company needs email and collaboration tools (Gmail, Slack)

---

**Comparison Table**

| Aspect | IaaS | PaaS | SaaS |
|--------|------|------|------|
| Control | High | Medium | Low |
| Management | You manage OS/apps | You manage only apps | Provider manages all |
| Flexibility | Most flexible | Less flexible | Least flexible |
| Time to deploy | Minutes to hours | Minutes | Instant |
| Use case | Lift-and-shift | Custom apps | Ready-to-use software |
| Examples | EC2, VMs | Heroku, App Engine | Gmail, Salesforce |

**Docker Basics**

**What is Docker?** A platform for developing, shipping, and running applications in containers.

**Key Components:**

1. **Dockerfile:** Instructions to build an image
2. **Image:** Blueprint for a container (read-only)
3. **Container:** Running instance of an image
4. **Registry:** Stores images (Docker Hub)

**Example Dockerfile:**

```dockerfile
# Use official Python image
FROM python:3.9-slim

# Set working directory
WORKDIR /app

# Copy requirements and install
COPY requirements.txt .
RUN pip install -r requirements.txt

# Copy application code
COPY . .

# Expose port
EXPOSE 8080

# Run the application
CMD ["python", "app.py"]
```

**Common Docker Commands:**

```bash
docker build -t myapp:latest .     # Build image
docker run -p 8080:8080 myapp      # Run container
docker ps                          # List running containers
docker stop <container_id>         # Stop container
docker rm <container_id>           # Remove container
docker images                      # List images
docker push myapp:latest           # Push to registry
```

## Chapter 7: High Availability

**What is High Availability?**

High Availability (HA) ensures a system remains operational and accessible even when some components fail. The goal is to minimize downtime.

**Key Metric: Uptime Percentage**

| Availability | Downtime per year | Downtime per month | Downtime per week |
|--------------|-------------------|--------------------|--------------------|
| 99% (2 nines) | 3.65 days | 7.2 hours | 1.68 hours |
| 99.9% (3 nines) | 8.76 hours | 43.2 minutes | 10.1 minutes |
| 99.99% (4 nines) | 52.56 minutes | 4.32 minutes | 1.01 minutes |
| 99.999% (5 nines) | 5.26 minutes | 25.9 seconds | 6 seconds |

**Diagram: Multi-Zone High Availability**

**Key High Availability Patterns**

1. **Load Balancing:** Distribute traffic across multiple instances
2. **Redundancy:** Multiple instances of each component
3. **Health Checks:** Detect failed instances
4. **Auto-Failover:** Automatic recovery when failures detected
5. **Multi-Zone Deployment:** Spread across availability zones

**Failover Systems**

**Active-Passive:** One active instance, one standby (waiting)

**Active-Active:** Multiple active instances, all serving traffic

## Chapter 9: Fault Tolerance

**What is Fault Tolerance?**

Fault tolerance is the ability of a system to continue operating properly even when some components fail.

**Fault Tolerance vs High Availability**

| Aspect | High Availability | Fault Tolerance |
|--------|-------------------|-----------------|
| **Goal** | Minimize downtime | Zero downtime |
| **Failure recovery** | Seconds to minutes | Instant (no interruption) |
| **Cost** | Moderate | High |
| **Complexity** | Moderate | High |
| **Example** | Load balancer + multiple servers | Redundant components with failover |

**Diagram: Fault Tolerance Strategies**

```

│  │  ┌──────────┐    ┌──────────┐    ┌──────────┐                  │ │

│  │  │ Active   │    │ Active   │    │ Active   │                  │ │
│  │  └──────────┘    └──────────┘    └──────────┘                  │ │
│  │                                                                   │ │

│  │  If primary fails, replica becomes primary                       │ │
│  │                                                                   │ │
│  └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│  3. CHECKPOINTING & BACKUP                                           │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │                                                                   │ │
│  │  ┌──────────┐    Periodic     ┌──────────┐                     │ │
│  │  │ Service  │ ──────────────▶ │ Backup   │                     │ │
│  │  │ State    │                  │ Storage  │                     │ │
│  │  └──────────┘                  └──────────┘                     │ │
│  │                                                                   │ │
│  │  Regular backups of state                                        │ │
│  │  Restore from last checkpoint on failure                         │ │
│  │                                                                   │ │
│  └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
└─────────────────────────────────────────────────────────────────────┘
```

**Backup Strategies**

| Strategy | Description | RPO (Recovery Point Objective) | RTO (Recovery Time Objective) |
|----------|-------------|-------------------------------|------------------------------|
| Daily backups | Back up once per day | Up to 24 hours | Hours |
| Hourly backups | Back up every hour | Up to 1 hour | 30-60 minutes |
| Continuous | Real-time replication | Seconds | Minutes |
| 3-2-1 Rule | 3 copies, 2 media types, 1 offsite | Varies | Varies |

## Chapter 12: Distributed Systems Basics

**CAP Theorem**

A distributed system can only provide two of three guarantees:

- **Consistency (C):** All nodes see same data at same time
- **Availability (A):** Every request receives a response
- **Partition Tolerance (P):** System continues despite network partitions

**Diagram: CAP Theorem**

```
┌─────────────────────────────────────────────────────────────────────┐
│                           CAP THEOREM                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                       │
│                              ┌─────────┐                             │
│                              │Consistency│                            │
│                              │   (C)   │                            │
│                              └────┬────┘                            │
│                                   │                                 │
│                    ┌──────────────┼──────────────┐                  │
│                    │              │              │                  │
│                    │              │              │                  │
│                    ▼              ▼              ▼                  │
│              ┌─────────┐    ┌─────────┐    ┌─────────┐            │
│              │   CP    │    │   CA    │    │   AP    │            │
│              │(ZooKeeper│    │(RDBMS)  │    │(Cassandra)│            │
│              │ etcd)   │    │         │    │DynamoDB)│            │
│              └─────────┘    └─────────┘    └─────────┘            │
│                    │              │              │                  │

│  CA: Consistency + Availability (single-node, not distributed)      │
│                                                                       │
└─────────────────────────────────────────────────────────────────────┘
```

**Consistency Models**

| Model | Description | Example |
|-------|-------------|---------|
| Strong Consistency | All reads see latest write | Relational DB |
| Eventual Consistency | Reads may see stale data | DNS, Cassandra |
| Causal Consistency | Related operations ordered | Some NoSQL |
| Read Your Writes | User sees their own writes | Session consistency |

# PART TWO: COMPUTE SERVICES

## Chapter 2: EC2 (Elastic Compute Cloud)

**What is EC2?**

Virtual servers in the cloud. You rent compute capacity (CPU, RAM, disk).

**Real Scenario**

Your startup needs to host a Node.js backend API. You expect traffic to grow over time.

**Without Cloud (Alternative):**
- Buy physical servers ($5,000+ upfront)
- Set up in a data center
- Wait weeks for delivery
- Manage hardware yourself
- Over-provision for peak or risk downtime

**With EC2:**
- Launch a t3.micro instance (1 vCPU, 1 GB RAM) for ~$8/month
- Scale up to larger instances as needed
- Pay only for what you use

**When to Use EC2**

- Need full control over OS and software
- Lift-and-shift existing applications
- Long-running workloads (24/7)
- Applications with specific OS requirements
- Need custom AMIs (Amazon Machine Images)

**EC2 vs Other AWS Compute**

| Service | Best for |
|---------|----------|
| **EC2** | Full control, long-running, custom apps |
| **Lambda** | Event-driven, short-running, serverless |
| **ECS/EKS** | Containers, microservices |

**Advantages**

- Full control over OS and software
- Wide variety of instance types (compute, memory, GPU optimized)
- Integration with other AWS services
- Auto-scaling capabilities
- Spot instances for cost savings (up to 90% off)

**Disadvantages**

- You manage OS updates, security patches
- Pay for idle time (if not optimized)
- More operational overhead than serverless

---

## Chapter 3: Lambda

**What is Lambda?**

Run code without provisioning or managing servers. Pay only for compute time when your code runs.

**Real Scenario**

You need to resize images whenever a user uploads to S3.

**Without Cloud (Alternative):**
- Run a server 24/7 waiting for uploads
- Waste resources when no uploads happen
- Manage scaling during traffic spikes

**With Lambda:**
- Function triggers on S3 upload event
- Runs only when images are uploaded
- Scales automatically (thousands of concurrent executions)
- Pay only for milliseconds of execution time

**Diagram: Lambda Flow**

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│  User    │ ──▶ │   S3     │ ──▶ │  Lambda  │
│  uploads │     │  upload  │     │  resize  │
│  image   │     │  event   │     │  image   │
└──────────┘     └──────────┘     └────┬─────┘
                                       │
                                       ▼
                                  ┌──────────┐
                                  │   S3     │
                                  │ resized  │
                                  │  image   │
                                  └──────────┘
```

**When to Use Lambda**

- Event-driven workloads (file processing, notifications)
- Short-running functions (<15 minutes)
- Variable or unpredictable traffic
- API backends (with API Gateway)
- Scheduled jobs (CloudWatch Events)

**Lambda vs EC2**

| Aspect | Lambda | EC2 |
|--------|--------|-----|
| **Server management** | None | You manage |
| **Scaling** | Automatic | You configure |
| **Cost** | Per execution | Per hour (even idle) |
| **Max execution time** | 15 minutes | Unlimited |
| **State** | Stateless | Can be stateful |
| **Use case** | Event-driven, microservices | Long-running apps |

**Advantages**

- No server management
- Automatic scaling
- Pay per execution (cost-effective for sporadic workloads)
- Built-in integrations with AWS services

**Disadvantages**

- 15-minute timeout limit
- Cold starts (first invocation delay)
- Limited runtime support
- Not suitable for long-running processes

# PART THREE: STORAGE SERVICES

## Chapter 4: S3 (Simple Storage Service)

**What is S3?**

Object storage for files, images, videos, backups, static websites. Unlimited storage, pay per GB.

**Real Scenario**

Your application needs to store user profile pictures and product images.

**Without Cloud (Alternative):**
- Set up file servers
- Manage disk space
- Implement backup and replication
- Handle scaling

**With S3:**
- Create an S3 bucket
- Upload files via API
- Automatic replication across AZs
- 11 nines of durability
- Pay only for what you store

**S3 Storage Classes**

| Class | Use Case | Durability | Availability |
|-------|----------|------------|--------------|
| **S3 Standard** | Frequently accessed data | 99.999999999% | 99.99% |
| **S3 Intelligent-Tiering** | Unknown access patterns | 99.999999999% | 99.9% |
| **S3 Standard-IA** | Infrequent access | 99.999999999% | 99.9% |
| **S3 One Zone-IA** | Recreatable data | 99.999999999% | 99.5% |
| **S3 Glacier** | Archives (minutes to hours retrieval) | 99.999999999% | — |
| **S3 Glacier Deep Archive** | Long-term archives (hours retrieval) | 99.999999999% | — |

**When to Use S3**

- Static website hosting
- File storage and sharing
- Backups and archives
- Data lake for analytics
- Media storage (images, videos)

**S3 vs EBS vs EFS**

| Aspect | S3 | EBS | EFS |
|--------|-----|-----|-----|
| **Type** | Object | Block | File |
| **Access** | API (HTTP) | Attached to EC2 | NFS (shared) |
| **Shared** | Yes (via API) | No | Yes |
| **Use case** | Static files, backups | Databases, boot volumes | Shared files |

**Advantages**

- Unlimited storage
- 99.999999999% durability (11 nines)
- Versioning support
- Lifecycle policies
- Server-side encryption
- Event notifications (S3 → Lambda)

**Disadvantages**

- Eventual consistency (for overwrites)
- No file system semantics (can't mount as drive)
- Request costs (GET, PUT requests cost money)

## Chapter 5: EBS vs EFS

**EBS (Elastic Block Store)**

Block storage for EC2 instances (like a hard drive).

**Real Scenario:** Your database needs high-performance, low-latency storage.

**When to use:** Boot volumes, databases, high-performance workloads.

**EFS (Elastic File System)**

File storage shared across multiple EC2 instances (like network drive).

**Real Scenario:** Multiple web servers need access to shared content files.

**When to use:** Shared content, home directories, logging.

**Comparison**

| Aspect | EBS | EFS |
|--------|-----|-----|
| **Access** | Single EC2 instance | Multiple EC2 instances (NFS) |
| **Performance** | High IOPS, low latency | Moderate |
| **Use case** | Databases, boot volumes | Shared files, home dirs |
| **Pricing** | Pay for provisioned capacity | Pay for used storage |
| **Backup** | Snapshots | Automatic |

## Chapter 7: Load Balancer (ALB vs NLB)

**What is Load Balancer?**

Distributes incoming traffic across multiple targets (EC2, Lambda, IP addresses).

**ALB (Application Load Balancer)**

Layer 7 (HTTP/HTTPS) load balancer.

**Best for:** Web applications, microservices, path-based routing.

**NLB (Network Load Balancer)**

Layer 4 (TCP/UDP) load balancer.

**Best for:** High performance, low latency, TCP/UDP traffic.

**Comparison**

| Aspect | ALB | NLB |
|--------|-----|-----|
| **Layer** | Layer 7 (HTTP/HTTPS) | Layer 4 (TCP/UDP) |
| **Routing** | Path-based, host-based, query string | IP-based, port-based |
| **Latency** | Moderate | Very low |
| **Static IP** | No (but can use Global Accelerator) | Yes |
| **Use case** | Web apps, APIs, microservices | High-performance TCP/UDP |

**IAM Best Practices**

1. **No root user access** (except initial setup)
2. **Use groups** to manage permissions
3. **Least privilege** (give minimum permissions needed)
4. **Use roles** for EC2, Lambda (never store credentials in code)
5. **Enable MFA** for privileged users
6. **Rotate access keys** regularly

## Chapter 15: EC2 vs Lambda vs ECS

| Aspect | EC2 | Lambda | ECS |
|--------|-----|--------|-----|
| **What it is** | Virtual servers | Serverless functions | Containers |
| **Control** | Full (OS, software) | None (just code) | Moderate |
| **Scaling** | Manual or auto-scaling | Automatic | Manual or auto-scaling |
| **Pricing** | Per hour | Per invocation | Per hour + resources |
| **State** | Can be stateful | Stateless | Can be stateful |
| **Max duration** | Unlimited | 15 minutes | Unlimited |
| **Best for** | Long-running, custom apps | Event-driven, sporadic | Microservices, portability |
| **Without Cloud** | Physical servers | Always-running server | Kubernetes clusters |
| **When to use** | Need full control, lift-and-shift | Short functions, variable traffic | Containers, microservices |

## Chapter 16: S3 vs EBS vs EFS

| Aspect | S3 | EBS | EFS |
|--------|-----|-----|-----|
| **Type** | Object | Block | File |
| **Access** | API (HTTP) | Attached to EC2 | NFS (shared) |
| **Shared** | Yes (via API) | No | Yes |
| **Size** | Unlimited | Up to 16 TB | Unlimited |
| **Performance** | Moderate | High IOPS | Moderate |
| **Use case** | Static files, backups | Databases, boot | Shared files |
| **Without Cloud** | File server | Hard drive | NAS (Network Attached Storage) |
| **When to use** | Files, images, backups | Databases, high I/O | Shared content |

## Chapter 17: RDS vs DynamoDB

| Aspect | RDS | DynamoDB |
|--------|-----|----------|
| **Type** | SQL (relational) | NoSQL (key-value/document) |
| **Schema** | Fixed (tables, columns) | Flexible (schema-less) |
| **Scaling** | Vertical (bigger instance) | Horizontal (automatic) |
| **Complex queries** | Yes (JOINs, aggregations) | Limited |
| **ACID transactions** | Yes | Limited (transactional APIs) |
| **Latency** | Millisecond | Single-digit millisecond |
| **Use case** | Complex queries, transactions | High scale, simple lookups |
| **Without Cloud** | Traditional DB server | NoSQL cluster |
| **When to use** | Structured data, SQL needed | High throughput, simple keys |

## Chapter 18: ALB vs NLB

| Aspect | ALB | NLB |
|--------|-----|-----|
| **Layer** | Layer 7 (HTTP/HTTPS) | Layer 4 (TCP/UDP) |
| **Routing** | Path-based, host-based | IP-based, port-based |
| **Latency** | Moderate | Very low |
| **Static IP** | No (via Global Accelerator) | Yes |
| **Target types** | EC2, Lambda, IP | EC2, IP |
| **Use case** | Web apps, APIs, microservices | High-performance TCP/UDP |
| **Without Cloud** | HAProxy, Nginx | Hardware load balancer |
| **When to use** | HTTP/HTTPS traffic, path routing | TCP/UDP, low latency, static IP |

# PART ELEVEN: INTERVIEW PREPARATION

## Chapter 19: Common AWS Interview Questions

**1. Q: What's the difference between EC2 and Lambda?**

**A:** EC2 is a virtual server you manage (OS, patches, scaling). Lambda is serverless—you just upload code, and AWS runs it on demand. Use EC2 for long-running, stateful applications. Use Lambda for event-driven, short-running functions.

**2. Q: How do you secure an S3 bucket?**

**A:** 
- Block public access by default
- Use bucket policies for access control
- Enable encryption (SSE-S3, SSE-KMS)
- Use IAM roles for application access
- Enable versioning to protect against deletions
- Enable access logging

**3. Q: Explain the difference between RDS and DynamoDB.**

**A:** RDS is SQL-based (relational) with fixed schema, supports complex queries (JOINs), and scales vertically. DynamoDB is NoSQL (key-value/document) with flexible schema, scales horizontally automatically, and is best for high throughput with simple lookup patterns.

**4. Q: What's a VPC and why use private subnets?**

**A:** VPC is a logically isolated network in AWS. Private subnets have no direct internet access, so databases and application servers are protected from external access. Only load balancers and web servers go in public subnets.

**5. Q: How does auto-scaling work?**

**A:** Auto-scaling groups maintain desired number of EC2 instances based on policies (CPU > 70%, schedule, custom metrics). It launches new instances when needed and terminates unhealthy or idle ones.
