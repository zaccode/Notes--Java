# PART ONE: AWS BASICS

## Chapter 1: What is AWS

**Simple Definition**

AWS (Amazon Web Services) is a cloud platform offering over 200 services including compute, storage, databases, networking, and machine learning—all available on demand over the internet.

**Real Scenario**

Your startup needs to host a website. You have two options:
- **Without AWS:** Buy servers ($10,000+), wait weeks, hire IT staff
- **With AWS:** Launch EC2 instance in 5 minutes, pay $0.042/hour

**AWS Global Infrastructure**

**Key Concepts**

| Concept | Description | Example | Why Important |
|---------|-------------|---------|---------------|
| **Region** | Geographic area | us-east-1 (Virginia), eu-west-1 (Ireland) | Latency, compliance, cost |
| **Availability Zone (AZ)** | One or more data centers | us-east-1a, us-east-1b | High availability (spread across AZs) |
| **Edge Location** | CDN endpoint | 400+ globally | Low latency content delivery |

**Why Regions Matter**

| Factor | Explanation |
|--------|-------------|
| **Latency** | Choose region closest to your users |
| **Compliance** | Data residency requirements (GDPR, etc.) |
| **Cost** | Prices vary by region (us-east-1 is cheapest) |
| **Service Availability** | New services launch in us-east-1 first |

**Global Services vs Regional Services**

| Type | Examples | Scope |
|------|----------|-------|
| **Global** | IAM, Route 53, CloudFront | Single configuration for all regions |
| **Regional** | EC2, S3, RDS, Lambda | Per-region resources |

## Chapter 2: EC2 (Elastic Compute Cloud)

**What is EC2?**

Virtual servers in the cloud. You rent compute capacity (CPU, RAM, disk) by the hour or second.

**Real Scenario**

Your company needs to host a Node.js backend API that runs 24/7.

**Without Cloud (Alternative):**
- Buy physical servers ($5,000+ upfront)
- Wait weeks for delivery
- Set up in a data center
- Manage hardware, cooling, power
- Hire IT staff
- Over-provision for peak or risk downtime

**With EC2:**
- Launch t3.micro instance (1 vCPU, 1 GB RAM) in 5 minutes
- Pay ~$0.0104/hour (~$7.50/month)
- Scale up to larger instances as traffic grows
- No hardware to manage

|--------|---------|---------|----------|
| **General Purpose (t, m)** | Balanced | t3.micro, m5.large | Web servers, small DBs |

| **Storage Optimized (i, d)** | High I/O | i3.large | NoSQL, data warehousing |

**EC2 Pricing Models**

| Model | Description | Best for |
|-------|-------------|----------|

| **Spot** | Bid for unused capacity (up to 90% off) | Fault-tolerant, batch jobs |
| **Savings Plans** | Flexible commitment across families | Mixed workloads |


**When to Use EC2**

| Use Case | Why EC2 |
|----------|---------|
| **Lift-and-shift migration** | Run existing apps without changes |
| **Long-running workloads** | 24/7 applications |
| **Custom software** | Need specific OS or software |
| **Legacy applications** | Require full control |
| **Batch processing** | Can use Spot instances for savings |

**When NOT to Use EC2**

| Use Case | Better Option |
|----------|---------------|
| **Event-driven** | Lambda (serverless) |
| **Sporadic traffic** | Lambda (pay per invocation) |
| **Containers** | ECS or EKS |
| **Static websites** | S3 + CloudFront |

**Advantages of EC2**

1. **Full control:** Choose OS, software, configuration
2. **Wide variety:** 400+ instance types for any workload
3. **Flexible pricing:** On-demand, reserved, spot
4. **Integration:** Works with all AWS services
5. **Auto scaling:** Automatically adjust capacity

**Disadvantages of EC2**

1. **Management overhead:** You manage OS, patches, security
2. **Pay for idle:** Pay even when not at full utilization
3. **Manual scaling:** Need to configure auto scaling
4. **State management:** You manage data persistence

**EC2 vs Other AWS Compute (Preview)**

| Aspect | EC2 | Lambda | ECS |
|--------|-----|--------|-----|
| **Control** | Full | None | Moderate |
| **Pricing** | Per hour | Per invocation | Per hour |
| **Startup** | Minutes | Milliseconds | Seconds |
| **State** | Can be stateful | Stateless | Can be stateful |
| **Max duration** | Unlimited | 15 minutes | Unlimited |

## Chapter 3: Lambda (Serverless Functions)

**What is Lambda?**

Run code without provisioning or managing servers. Upload your code, and Lambda runs it on demand. Pay only for compute time when your code runs.

**Real Scenario**

Your application needs to resize images whenever a user uploads a profile picture.

**Without Cloud (Alternative):**
- Run an EC2 instance 24/7 waiting for uploads
- Waste resources when no uploads happen (95% idle)
- Manage scaling during traffic spikes
- Handle server maintenance

**With Lambda:**
- Function triggers automatically on S3 upload
- Runs only when images are uploaded
- Scales automatically to thousands of concurrent executions
- Pay only for milliseconds of execution time

**Diagram: Lambda Execution Flow**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           LAMBDA EXECUTION                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                               │
│  ┌──────────┐                                                               │
│  │  User    │                                                               │
│  │  uploads │                                                               │
│  │  image   │                                                               │
│  └────┬─────┘                                                               │
│       │                                                                      │
│       ▼                                                                      │
│  ┌─────────────────────────────────────────────────────────────────────────┐│
│  │                              S3                                          ││
│  │                         (Image upload)                                   ││
│  │                                                                           ││
│  │  Event: s3:ObjectCreated                                                 ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│       │                                                                      │
│       │ Trigger                                                             │
│       ▼                                                                      │
│  ┌─────────────────────────────────────────────────────────────────────────┐│

│  │                      (Image Resize Function)                             ││
│  │                                                                           ││
│  │  1. Download original image from S3                                     ││
│  │  2. Resize image (128x128)                                               ││

│  │                              S3                                          ││
│  │                      (Resized image stored)                              ││
│  └─────────────────────────────────────────────────────────────────────────┘│
│                                                                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Lambda Sample Code (Node.js)**

```javascript
// Image resize Lambda function
const AWS = require('aws-sdk');
const sharp = require('sharp');

const s3 = new AWS.S3();

exports.handler = async (event) => {
    // Get the uploaded image from S3 event
    const bucket = event.Records[0].s3.bucket.name;
    const key = decodeURIComponent(event.Records[0].s3.object.key);
    
    // Download original image
    const originalImage = await s3.getObject({ Bucket: bucket, Key: key }).promise();
    
    // Resize image (128x128)
    const resizedImage = await sharp(originalImage.Body)
        .resize(128, 128)
        .toBuffer();
    
    // Upload resized image to different bucket
    await s3.putObject({
        Bucket: 'my-resized-images',
        Key: `resized/${key}`,
        Body: resizedImage,
        ContentType: 'image/jpeg'
    }).promise();
    
    return {
        statusCode: 200,
        body: JSON.stringify({ message: 'Image resized successfully' })
    };
};
```

**Lambda Triggers (Event Sources)**

| Trigger | Use Case |
|---------|----------|
| **API Gateway** | REST API backend |
| **S3** | File processing on upload |
| **DynamoDB Streams** | React to database changes |
| **SQS** | Process queue messages |
| **SNS** | Handle notifications |
| **CloudWatch Events** | Scheduled jobs (cron) |
| **Kinesis** | Stream processing |

**Lambda Limits**

| Limit | Value |
|-------|-------|
| **Timeout** | 15 minutes maximum |
| **Memory** | 128 MB - 10 GB |
| **Temporary disk (/tmp)** | 512 MB - 10 GB |
| **Request size** | 6 MB (sync), 256 KB (async) |
| **Concurrent executions** | 1,000 (soft limit, can increase) |
| **Function size** | 50 MB (zipped), 250 MB (unzipped) |

**Lambda Pricing (as of 2024)**

- **Compute:** $0.0000166667 per GB-second
- **Requests:** $0.20 per 1 million requests
- **Free tier:** 1 million requests/month + 400,000 GB-seconds

**Example pricing:**
- 1 million requests @ 128 MB for 100ms = ~$0.20 (requests) + $0.21 (compute) = $0.41

**When to Use Lambda**

| Use Case | Why Lambda |
|----------|------------|
| **Event-driven processing** | Respond to events (S3, DynamoDB) |
| **API backends** | With API Gateway |
| **File processing** | Images, videos, documents |
| **Data transformation** | ETL pipelines |
| **Scheduled tasks** | CloudWatch Events (cron) |
| **Chatbots** | Alexa skills, Slack bots |

**When NOT to Use Lambda**

| Use Case | Better Option |
|----------|---------------|
| **Long-running processes (>15 min)** | EC2 or ECS |
| **Stateful applications** | EC2 |
| **Low-latency (<10ms) requirements** | EC2 (warm) |
| **Compute-intensive workloads** | EC2 (GPU instances) |
| **Large deployments** | EC2 or containers |

**Advantages of Lambda**

1. **No server management:** Focus on code, not infrastructure
2. **Automatic scaling:** From 0 to thousands of concurrent executions
3. **Pay per use:** No cost when not running
4. **Built-in integrations:** S3, DynamoDB, API Gateway, etc.
5. **Multi-language support:** Node.js, Python, Java, Go, .NET, Ruby

**Disadvantages of Lambda**

1. **Cold starts:** First invocation can be slow (100ms-1s)
2. **Timeout limit:** 15 minutes maximum
3. **Stateless:** No local state between invocations
4. **Debugging complexity:** Harder than EC2
5. **Vendor lock-in:** Lambda-specific features

**Lambda vs EC2 (Preview)**

| Aspect | Lambda | EC2 |
|--------|--------|-----|
| **Pricing** | Per invocation | Per hour (even idle) |
| **Scaling** | Automatic | Manual/Auto Scaling |
| **Cold start** | Yes (100ms-1s) | No |
| **Control** | None | Full |
| **Best for** | Event-driven, sporadic | Long-running, custom |

## Chapter 4: ECS & EKS (Container Services)

**What is ECS?**

Elastic Container Service is AWS's native container orchestration service. Run and scale Docker containers on AWS.

**What is EKS?**

Elastic Kubernetes Service is managed Kubernetes on AWS. Run Kubernetes without managing the control plane.

**Real Scenario**

Your team has containerized a microservices application (Docker images). You need to run and scale these containers.

**Without Cloud (Alternative):**
- Set up Kubernetes cluster (weeks of work)
- Manage control plane (etcd, API server, scheduler)
- Handle upgrades, patches, security
- Scale infrastructure yourself

**With ECS/EKS:**
- Deploy containers in minutes
- AWS manages control plane (EKS) or simpler (ECS)
- Automatic scaling of containers
- Integrated with AWS services (ALB, IAM, CloudWatch)

| **Type** | AWS native | Kubernetes (open source) |
| **Complexity** | Simpler | More complex |
| **Control plane** | Managed by AWS | Managed by AWS (EKS) |
| **Portability** | AWS only | Multi-cloud (K8s) |
| **Learning curve** | Lower | Higher |
| **Community** | Smaller | Large (open source) |
| **Tooling** | AWS tools | kubectl, Helm, Istio |
| **When to use** | AWS-only, simpler needs | Portability, K8s expertise |

**When to Use ECS**

| Use Case | Why ECS |
|----------|---------|
| **AWS-only environment** | No need for portability |
| **Simplicity** | Easier than Kubernetes |
| **Deep AWS integration** | IAM, ALB, CloudWatch |
| **Serverless containers** | Fargate launch type |

**When to Use EKS**

| Use Case | Why EKS |
|----------|---------|
| **Multi-cloud strategy** | Run same K8s on AWS, GCP, Azure |
| **Existing Kubernetes expertise** | Team already knows K8s |
| **Open source tooling** | Helm, Istio, Prometheus |
| **Hybrid deployments** | On-prem + cloud K8s |

**Advantages of ECS**

1. **Simpler:** Easier to learn and operate
2. **Native integration:** Works seamlessly with AWS services
3. **Fargate option:** No EC2 management
4. **Fast deployment:** Quick to set up

**Disadvantages of ECS**

1. **Vendor lock-in:** AWS only
2. **Smaller ecosystem:** Fewer third-party tools
3. **Less community support**

**Advantages of EKS**

1. **Portability:** Run on any cloud or on-premises
2. **Large ecosystem:** Helm, Istio, Prometheus, Grafana
3. **Community support:** Large open source community
4. **Flexibility:** Customizable with CRDs and operators

**Disadvantages of EKS**

1. **Complexity:** Steeper learning curve
2. **Management overhead:** Still need to manage worker nodes
3. **Cost:** $0.10 per hour for control plane

**What is S3?**

Object storage for files, images, videos, backups, and static websites. Unlimited storage, pay per GB stored and per request.

**Real Scenario**

Your application needs to store user profile pictures and product images.

**Without Cloud (Alternative):**

```bash

# Sync directory
aws s3 sync ./local-folder s3://my-app-bucket/folder/

# Set bucket policy (public read for static website)
aws s3api put-bucket-policy --bucket my-app-bucket --policy '{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-app-bucket/*"
  }]
}'
```

**When to Use S3**

| Use Case | Why S3 |
|----------|--------|
| **Static websites** | HTML, CSS, JS files |
| **User uploads** | Profile pictures, documents |
| **Backups** | Database backups, logs |
| **Data lakes** | Analytics, ML training data |
| **Media storage** | Images, videos |
| **Distributing software** | Installers, packages |

**Advantages of S3**

1. **11 nines durability:** 99.999999999% (you won't lose data)
2. **Unlimited storage:** No capacity planning
3. **Pay per use:** No minimum fees
4. **Global namespace:** Bucket names are globally unique
5. **Integration:** Works with all AWS services

**Disadvantages of S3**

1. **Eventual consistency:** For overwrites and deletes
2. **No file system semantics:** Can't mount as a drive
3. **Request costs:** GET, PUT requests cost money
4. **Not for live files:** Not suitable for frequently updating files

## Chapter 6: EBS (Elastic Block Store)

**What is EBS?**

Block storage for EC2 instances. Like a hard drive you attach to your EC2 instance. Can only be attached to one instance at a time.

**Real Scenario**

Your EC2 instance needs high-performance, low-latency storage for a database.

**Without Cloud (Alternative):**
- Install physical hard drive in server
- Limited capacity (add more drives)
- No backup automation
- Manual replacement on failure

**With EBS:**
- Create EBS volume in seconds
- Attach to EC2 instance
- 1 GB to 16 TB per volume
- Automatic backups (snapshots)

|---------|-------------|
| **Snapshots** | Point-in-time backups to S3 |
| **Encryption** | AES-256 encryption at rest |
| **Multi-attach** | io1/io2 can attach to multiple instances (limited) |
| **Elastic volumes** | Modify size, type, IOPS without downtime |

**EBS vs Instance Store**

| Aspect | EBS | Instance Store |
|--------|-----|----------------|
| **Persistence** | Data persists after stop/terminate | Data lost on stop |
| **Backup** | Snapshots | No built-in backup |
| **Performance** | High | Very high (local NVMe) |
| **Use case** | Databases, boot volumes | Temporary data, cache |

**When to Use EBS**

| Use Case | Why EBS |
|----------|---------|
| **Boot volumes** | Root disk for EC2 |
| **Databases** | MySQL, PostgreSQL, MongoDB |
| **Application data** | Files that need persistence |
| **High IOPS workloads** | Provisioned IOPS (io1/io2) |

**Advantages of EBS**

1. **Persistent storage:** Data survives EC2 stop/start
2. **Snapshots:** Easy backups to S3
3. **Elastic:** Resize without downtime
4. **Encryption:** Built-in encryption
5. **Performance:** High IOPS and throughput

**Disadvantages of EBS**

1. **Single attachment:** Can't share across instances (except multi-attach)
2. **Cost:** More expensive than S3 per GB
3. **AZ bound:** Can't move across availability zones

**What is VPC?**

**With VPC:**
- Define IP range (10.0.0.0/16)
- Create public and private subnets

- All in software, minutes to create

|-----------|-------------|---------|
| **CIDR Block** | IP range (e.g., 10.0.0.0/16) | Defines VPC address space |
| **Subnet** | Range of IPs within VPC | Isolate resources |
| **Internet Gateway** | Connects VPC to internet | Public internet access |
| **NAT Gateway** | Private subnet → internet | Software updates, APIs |
| **Route Table** | Rules for traffic routing | Direct traffic |
| **Security Group** | Instance-level firewall | Allow/deny traffic |
| **NACL** | Subnet-level firewall | Additional security layer |
| **VPC Peering** | Connect two VPCs | Cross-VPC communication |
| **VPN Gateway** | Connect to on-premises | Hybrid cloud |

**Security Groups vs NACLs**

| Aspect | Security Group | NACL (Network ACL) |
|--------|----------------|--------------------|
| **Level** | Instance | Subnet |
| **State** | Stateful (return allowed) | Stateless (rules both ways) |
| **Rules** | Only Allow | Allow and Deny |
| **Order** | All evaluated | Rules in order (first match) |
| **Use case** | Instance security | Subnet security |

**When to Use VPC**

| Use Case | Why VPC |
|----------|---------|
| **Any AWS deployment** | Required for EC2, RDS, etc. |
| **Multi-tier apps** | Separate web, app, DB layers |
| **Security compliance** | Isolated network |
| **Hybrid cloud** | VPN to on-premises |

**Advantages of VPC**

1. **Isolation:** Your own private network in AWS
2. **Control:** Define IP ranges, routing, security
3. **Scalability:** Add subnets, gateways as needed
4. **Hybrid connectivity:** VPN or Direct Connect to on-premises

**Disadvantages of VPC**

1. **Complexity:** Need networking knowledge
2. **Planning required:** CIDR choices can't be changed easily
3. **Limits:** Default limits (5 VPCs per region, 200 subnets per VPC)

Distributes incoming traffic across multiple targets (EC2 instances, Lambda functions, IP addresses).

**Real Scenario**

Your web application runs on 3 EC2 instances. You need to distribute user traffic across them.

**Without Cloud (Alternative):**
- Set up HAProxy or Nginx as load balancer

- Handle failover
- Manage scaling

**With AWS Load Balancer:**
- Create ALB in minutes
- Automatic health checks
- Integration with Auto Scaling
- Fully managed

**ALB (Application Load Balancer) - Layer 7**

| Feature | Description |
|---------|-------------|
| **Protocols** | HTTP, HTTPS, gRPC |
| **Routing** | Path-based (/api/*, /admin/*), host-based (api.example.com) |
| **Targets** | EC2, Lambda, ECS, IP addresses |
| **Features** | Sticky sessions, authentication, WAF integration |

**NLB (Network Load Balancer) - Layer 4**

| Feature | Description |
|---------|-------------|
| **Protocols** | TCP, UDP, TLS |
| **Routing** | IP-based, port-based |
| **Targets** | EC2, IP addresses |
| **Features** | Static IP, very low latency, millions of requests/sec |

**ALB vs NLB Comparison**

| Aspect | ALB | NLB |
|--------|-----|-----|
| **Layer** | Layer 7 (HTTP/HTTPS) | Layer 4 (TCP/UDP) |
| **Latency** | Moderate (HTTP processing) | Very low (pass-through) |
| **Routing** | Path, host, query string | IP, port |
| **Static IP** | No (use Global Accelerator) | Yes |
| **Targets** | EC2, Lambda, ECS, IP | EC2, IP |
| **Use case** | Web apps, APIs, microservices | High performance, TCP/UDP |
| **Price** | Moderate | Lower |

**When to Use ALB**

| Use Case | Why ALB |
|----------|---------|
| **Web applications** | HTTP/HTTPS traffic |
| **Microservices** | Path-based routing (/users, /orders) |
| **API Gateway alternative** | Simple API needs |
| **Lambda targets** | Serverless backends |

| Use Case | Why Route 53 |

**Advantages of Route 53**

**Disadvantages of Route 53**

**Disadvantages of DynamoDB**

4. **Transactions:** Limited ACID support

**CDK Example (TypeScript)**

```typescript
import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as rds from 'aws-cdk-lib/aws-rds';

export class MyStack extends cdk.Stack {
  constructor(scope: cdk.App, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    // Create VPC
    const vpc = new ec2.Vpc(this, 'MyVpc', {
      maxAzs: 2,
      natGateways: 1,
    });

    // Create EC2 instance
    const webServer = new ec2.Instance(this, 'WebServer', {
      vpc,
      instanceType: ec2.InstanceType.of(
        ec2.InstanceClass.T3,
        ec2.InstanceSize.MICRO
      ),
      machineImage: ec2.MachineImage.latestAmazonLinux2(),
    });

    // Create RDS database
    const database = new rds.DatabaseInstance(this, 'Database', {
      engine: rds.DatabaseInstanceEngine.postgres({
        version: rds.PostgresEngineVersion.VER_13,
      }),
      instanceType: ec2.InstanceType.of(
        ec2.InstanceClass.T3,
        ec2.InstanceSize.MICRO
      ),
      vpc,
    });
  }
}
```

## Chapter 17: IAM (Identity and Access Management)

**What is IAM?**

Manage access to AWS services and resources. Create users, groups, roles, and define permissions with policies.

**Real Scenario**

Your development team needs access to EC2 (create, stop, start), but not to billing or IAM.

**Without Cloud (Alternative):**
- Separate AWS accounts (hard to manage)
- Shared root credentials (dangerous)
- No fine-grained permissions

**With IAM:**
- Create IAM users for each developer
- Assign to "Developers" group
- Attach policy allowing EC2 actions
- Enforce MFA for privileged actions

**IAM Best Practices**

| Practice | Why |
|----------|-----|
| **No root user access** | Root has full permissions, use only for initial setup |
| **Enable MFA** | Adds security layer for privileged actions |
| **Use groups** | Manage permissions by role, not per user |
| **Least privilege** | Give minimum permissions needed |
| **Use roles for EC2** | Never store credentials on EC2 |
| **Rotate keys regularly** | Reduce risk of compromised keys |
| **Audit policies** | Use IAM Access Analyzer, CloudTrail |
| **Use conditions** | Restrict by IP, time, MFA |

**When to Use IAM**

| Use Case | Why IAM |
|----------|---------|
| **User management** | Create AWS users for employees |
| **Service permissions** | Give EC2 access to S3 via roles |
| **Federated access** | Connect corporate Active Directory |
| **Fine-grained control** | Restrict by resource, action, condition |

**Advantages of IAM**

1. **Fine-grained control:** Allow/deny specific actions on specific resources
2. **Centralized management:** One place for all permissions
3. **Integration:** Works with all AWS services
4. **Federation:** Connect to Active Directory, Google, etc.
5. **Audit:** CloudTrail logs all IAM actions

**Disadvantages of IAM**

1. **Complexity:** Policies can become complex
2. **Propagation delays:** Changes take seconds to minutes
3. **Quotas:** Limits on users, groups, roles (can be increased)
4. **Global:** IAM is global (affects all regions)

## Chapter 18: Security Groups & NACLs

**What are Security Groups?**

Virtual firewall for EC2 instances. Control inbound and outbound traffic at the instance level.

**What are NACLs?**

Network Access Control Lists. Stateless firewall for subnets.

**Real Scenario**

Your web server should accept HTTP/HTTPS from anywhere, but SSH only from office IP. Your database should accept only from web server.

**Without Cloud (Alternative):**
- Configure iptables on each server
- Manual updates
- No centralized management

**With Security Groups:**
- Create security group for web servers
- Allow HTTP (0.0.0.0/0), SSH (office IP)
- Create security group for database
- Allow MySQL from web security group

**Diagram: Security Groups & NACLs**

**Security Groups vs NACLs**

| Aspect | Security Group | NACL |
|--------|----------------|------|
| **Level** | Instance | Subnet |
| **State** | Stateful (return traffic allowed) | Stateless (rules both ways) |
| **Rules** | Only Allow | Allow and Deny |
| **Order** | All rules evaluated | Rules in numeric order (first match) |
| **Default** | Deny all inbound, allow all outbound | Allow all inbound and outbound |
| **Use case** | Instance-level security | Subnet-level defense in depth |

**Common Security Group Rules**

| Rule | Type | Protocol | Port | Source | Purpose |
|------|------|----------|------|--------|---------|
| SSH | Inbound | TCP | 22 | Office IP | Admin access |
| HTTP | Inbound | TCP | 80 | 0.0.0.0/0 | Web traffic |
| HTTPS | Inbound | TCP | 443 | 0.0.0.0/0 | Web traffic |
| MySQL | Inbound | TCP | 3306 | App SG | Database access |
| Outbound | Outbound | All | All | 0.0.0.0/0 | General internet |

**Best Practices**

| Practice | Why |
|----------|-----|
| **Use security groups** | Simpler, stateful |
| **Least privilege** | Only open required ports |
| **Restrict SSH** | Only from office IP or bastion |
| **Use security group references** | Reference by ID, not IP |
| **Audit rules** | Regular review of open ports |
| **Log VPC Flow Logs** | Monitor traffic patterns |

**What is Secrets Manager?**

Securely store, rotate, and manage secrets (database credentials, API keys, OAuth tokens).

**What is KMS (Key Management Service)?**

**Secrets Manager vs Parameter Store**

| Aspect | Secrets Manager | Parameter Store |
|--------|-----------------|-----------------|
| **Cost** | $0.40 per secret/month | $0.05 per parameter/month |
| **Rotation** | Built-in automatic rotation | Manual or Lambda |
| **Encryption** | Always encrypted | Optional (SecureString) |
| **Secret size** | Up to 10 KB | Up to 8 KB |
| **Use case** | Secrets (passwords, API keys) | Config values (database URL) |

**KMS Key Types**

| Type | Description | Use Case |
|------|-------------|----------|
| **AWS managed** | Created by AWS (aws/service-name) | Default encryption |
| **Customer managed** | You create and manage | Custom requirements |
| **Custom key store** | Keys in CloudHSM | Regulatory compliance |

**When to Use Secrets Manager & KMS**

| Use Case | Why Secrets Manager | Why KMS |
|----------|--------------------|---------|
| **Database passwords** | Automatic rotation | Encryption |
| **API keys** | Secure storage | Encryption |
| **Third-party tokens** | Central management | Encryption |
| **S3 encryption** | — | Server-side encryption |
| **EBS encryption** | — | Volume encryption |

**Advantages of Secrets Manager**

1. **Automatic rotation:** Built-in for RDS, Redshift, DocumentDB
2. **Audit:** CloudTrail logs secret access
3. **Integration:** Works with Lambda for custom rotation
4. **Secure:** Encrypted with KMS

**Disadvantages of Secrets Manager**

1. **Cost:** More expensive than Parameter Store
2. **Limits:** 500,000 secrets per region
3. **Latency:** API call adds latency

**Lambda Function Example (createUser)**

```javascript
// createUser Lambda function
const AWS = require('aws-sdk');
const dynamodb = new AWS.DynamoDB.DocumentClient();
const sns = new AWS.SNS();

exports.handler = async (event) => {
    try {
        // Parse request body
        const { name, email } = JSON.parse(event.body);
        
        // Validate input
        if (!name || !email) {
            return {
                statusCode: 400,
                body: JSON.stringify({ error: 'Missing name or email' })
            };
        }
        
        // Generate user ID
        const userId = `user_${Date.now()}`;
        
        // Save to DynamoDB
        await dynamodb.put({
            TableName: process.env.USERS_TABLE,
            Item: {
                userId,
                name,
                email,
                createdAt: new Date().toISOString()
            }
        }).promise();
        
        // Publish event to SNS (send welcome email)
        await sns.publish({
            TopicArn: process.env.WELCOME_TOPIC,
            Message: JSON.stringify({ userId, email, name })
        }).promise();
        
        return {
            statusCode: 201,
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ userId, name, email })
        };
    } catch (error) {
        console.error(error);
        return {
            statusCode: 500,
            body: JSON.stringify({ error: 'Internal server error' })
        };
    }
};
```

```typescript
    users.addMethod('POST', new apigateway.LambdaIntegration(createUserLambda));
```

```javascript
const AWS = require('aws-sdk');
const sharp = require('sharp');
const s3 = new AWS.S3();

exports.handler = async (event) => {
    // Get S3 event
    const bucket = event.Records[0].s3.bucket.name;
    const key = decodeURIComponent(event.Records[0].s3.object.key);
    
    // Download original image
    const original = await s3.getObject({ Bucket: bucket, Key: key }).promise();
    const image = original.Body;
    
    // Resize images in parallel
    const [thumbnail, medium] = await Promise.all([
        sharp(image).resize(128, 128).toBuffer(),
        sharp(image).resize(512, 512).toBuffer()
    ]);
    
    // Upload processed images
    await Promise.all([
        s3.putObject({
            Bucket: process.env.PROCESSED_BUCKET,
            Key: `thumbnail/${key}`,
            Body: thumbnail,
            ContentType: 'image/jpeg'
        }).promise(),
        s3.putObject({
            Bucket: process.env.PROCESSED_BUCKET,
            Key: `medium/${key}`,
            Body: medium,
            ContentType: 'image/jpeg'
        }).promise()
    ]);
    
    // Notify other services
    const sns = new AWS.SNS();
    await sns.publish({
        TopicArn: process.env.IMAGE_PROCESSED_TOPIC,
        Message: JSON.stringify({ originalKey: key, thumbnailKey: `thumbnail/${key}` })
    }).promise();
};
```

## Chapter 23: EC2 vs Lambda vs ECS

| Aspect | EC2 | Lambda | ECS |
|--------|-----|--------|-----|
| **What it is** | Virtual server | Serverless function | Container orchestration |
| **Control** | Full (OS, software) | None (just code) | Moderate (container) |
| **Pricing** | Per hour (even idle) | Per invocation (no idle) | Per hour + resources |
| **Scaling** | Manual or Auto Scaling | Automatic | Manual or Auto Scaling |
| **Startup time** | Minutes | Milliseconds (cold start) | Seconds |
| **Max duration** | Unlimited | 15 minutes | Unlimited |
| **State** | Can be stateful | Stateless | Can be stateful |
| **Best for** | Long-running, custom apps | Event-driven, sporadic | Microservices, portability |
| **Without cloud** | Physical server | Always-running server | Kubernetes cluster |
| **When to use** | Lift-and-shift, legacy | File processing, APIs | Containers, microservices |

**Decision Tree**

```
Start: Do you have existing code in containers?
    │
    ├── Yes → ECS (or EKS if you need Kubernetes)
    │
    └── No → Is your workload event-driven or sporadic?
            │
            ├── Yes → Lambda
            │
            └── No → Do you need full OS control?
                    │
                    ├── Yes → EC2
                    │
                    └── No → Lambda (if possible) or ECS
```

| Aspect | ALB | NLB |

# PART TEN: INTERVIEW PREPARATION

## Chapter 27: Common AWS Interview Questions

**1. Q: What's the difference between EC2 and Lambda?**

**A:** EC2 is a virtual server you manage (OS, patches, scaling). Lambda is serverless—you just upload code, and AWS runs it on demand. EC2 is for long-running, stateful applications. Lambda is for event-driven, short-running functions. EC2 costs per hour (even idle), Lambda costs per invocation (no idle cost).

**2. Q: How do you secure an S3 bucket?**

**A:** 
- Block public access by default (block public access settings)
- Use bucket policies for granular access control
- Enable encryption at rest (SSE-S3, SSE-KMS)
- Use IAM roles for application access
- Enable versioning to protect against accidental deletions
- Enable access logging to track requests
- Use pre-signed URLs for temporary access

**3. Q: Explain the difference between RDS and DynamoDB.**

**A:** RDS is SQL-based (relational) with fixed schema, supports complex queries (JOINs), and scales vertically (bigger instance). DynamoDB is NoSQL (key-value/document) with flexible schema, scales horizontally automatically, and is best for high throughput with simple lookup patterns. Use RDS for complex transactions and reporting; use DynamoDB for high-scale, low-latency key-value access.

**4. Q: What's a VPC and why use private subnets?**

**A:** VPC is a logically isolated network in AWS where you launch resources. Private subnets have no direct internet access, so databases and application servers are protected from external access. Only load balancers and web servers go in public subnets. Private subnets can access internet via NAT Gateway for updates.

**5. Q: How does auto scaling work?**

**A:** Auto Scaling Groups maintain desired number of EC2 instances based on policies (CPU > 70% for 5 minutes, scheduled scaling, custom metrics). It launches new instances when needed and terminates unhealthy or idle ones. Works with load balancers to distribute traffic.

**6. Q: What is IAM? What's the difference between user, group, role, and policy?**

**A:** IAM manages access to AWS services.

- **User:** Individual person with credentials
- **Group:** Collection of users (same permissions)
- **Role:** Assumed by AWS services (no credentials)
- **Policy:** JSON document defining permissions

**7. Q: What's the difference between security group and NACL?**

**A:** Security Group is instance-level, stateful (return traffic automatically allowed), only Allow rules. NACL is subnet-level, stateless (rules needed for both directions), supports Allow and Deny rules with priority order.

**8. Q: How would you design a highly available application on AWS?**

**A:** 
- Deploy across multiple Availability Zones (AZs)
- Use load balancer (ALB/NLB) to distribute traffic
- Use Auto Scaling Group for compute
- Use RDS Multi-AZ for database failover
- Use S3 for static assets (11 nines durability)
- Use CloudFront CDN for global distribution
- Use Route 53 for DNS failover

**9. Q: What's CloudFormation and why use it?**

**A:** CloudFormation is Infrastructure as Code (IaC) service that models and provisions AWS resources using templates. Benefits: version-controlled infrastructure, repeatable deployments, consistent environments, rollback on failure, dependency management.

**10. Q: What's the difference between ALB and NLB?**

**A:** ALB is Layer 7 (HTTP/HTTPS) with path-based routing, sticky sessions. NLB is Layer 4 (TCP/UDP) with lower latency, static IP. Use ALB for web apps, APIs. Use NLB for high-performance TCP/UDP, gaming.

## Chapter 29: Troubleshooting Scenarios

**Scenario 1: EC2 Instance Unreachable**

**Symptoms:** Cannot SSH into EC2 instance.

**Troubleshooting Steps:**
1. Check Security Group inbound rules (SSH port 22 open, source IP correct)
2. Check NACL rules (inbound/outbound for port 22)
3. Check instance status (running, not terminated)
4. Check route table (instance has route to internet)
5. Check internet gateway (attached to VPC)
6. Check system log (EC2 console → Actions → Instance Settings → Get System Log)

**Scenario 2: S3 Access Denied**

**Symptoms:** Cannot access S3 bucket (AccessDenied error).

**Troubleshooting Steps:**
1. Check IAM policy for your user/role
2. Check bucket policy (allows your principal)
3. Check bucket ACLs (if using)
4. Check bucket public access block settings
5. Check object ownership (ACL disabled?)
6. Check encryption settings (KMS key permissions)

**Scenario 3: Lambda Function Timeout**

**Symptoms:** Lambda function times out after 3 seconds.

**Troubleshooting Steps:**
1. Check Lambda timeout setting (default 3 seconds, increase if needed)
2. Check external API calls (are they hanging?)
3. Check database connection (is it established?)
4. Check for infinite loops
5. Check memory (low memory = slower execution)
6. Check CloudWatch logs for errors

**Scenario 4: RDS Connection Issues**

**Symptoms:** Application cannot connect to RDS.

**Troubleshooting Steps:**
1. Check RDS security group (allow inbound from app on port 3306/5432)
2. Check RDS is in same VPC as application
3. Check RDS is publicly accessible (if from internet)
4. Check username/password (Secrets Manager)
5. Check RDS instance status (available)
6. Check max connections limit
